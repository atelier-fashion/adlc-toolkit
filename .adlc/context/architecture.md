# Architecture — ADLC Toolkit

## Top-level layout

```
adlc-toolkit/
├── ETHOS.md                    # the ETHOS principles — injected into every skill
├── README.md                   # Install (plugin route first, then symlink) + skill catalog
├── RELEASING.md                # The maintainer's release and directory-submission sequence
├── VERSION                     # The release version; every plugin manifest pins the same string
├── .claude-plugin/             # plugin.json (plugin `adlc`) and marketplace.json (marketplace `adlc-toolkit`)
├── .cursor-plugin/             # plugin.json: the pinned catalog mount for Cursor (REQ-665)
├── .github/plugin/             # plugin.json: the pinned catalog mount for Copilot CLI (REQ-665)
├── hooks/hooks.json            # The plugin's one SessionStart hook
├── scripts/                    # session-start.sh (the hook) and adlc (the CLI shim on the plugin route)
├── <skill>/SKILL.md            # One directory per skill (spec/, architect/, proceed/, etc.)
├── <skill>/references/*.md     # A skill's companions, read when SKILL.md says (REQ-661)
├── agents/<agent>.md           # Specialized subagent definitions
├── templates/*.md              # Canonical templates (copied into consumer projects by /init)
├── partials/                   # Shared snippets (ethos macro, delegate gate, trial-merge) sourced by SKILL.md files
├── workflows/                  # Deterministic Dynamic Workflow scripts + schemas (copied into consumer projects by /init)
├── space/                      # The static Hugging Face Space for /spec intake (REQ-670), not part of any install
└── .adlc/                      # Minimal self-tracking for toolkit-internal REQs
    ├── context/                # This directory — project-overview, architecture, conventions
    └── specs/REQ-xxx-*/        # Requirement specs for toolkit changes
```

## Skill anatomy

Every skill is a markdown file at `<skill-name>/SKILL.md`, under 500 lines (`tools/lint-skills`' `skill-line-budget`, REQ-661), with this shape:

1. **Frontmatter**: `name`, `description`, optional `argument-hint`
2. **Title + one-line framing** — what the skill does
3. **Ethos injection**: the one `!` preamble line a skill keeps, byte-identical in every skill (conventions.md "Ethos injection pattern"). It reads the project's vendored `.adlc/ETHOS.md` only, and on Claude Code it is the only path that reaches a skill invoked inside a subagent (plan M6). `tools/lint-skills`' `ethos-line` check holds it there
4. **Context**: a `## Context` section whose body is one run-and-read fence, first line `# adlc-context`, that the model runs with its shell tool before anything else and reads the output of (REQ-666 BR-2). Each read prints a notice instead of failing when its file is absent, so the fence always exits 0. It replaced the `!` context lines, which other harnesses show as text and which abort a Claude Code invocation when one fails
5. **Input**: prose saying the argument is whatever follows the skill name in the invocation, and what the skill does with none (REQ-666 BR-1). No skill writes `$ARGUMENTS`; a fence that needs the value carries a single-quoted placeholder that the model fills by conventions.md's "Substituting a value into a fence"
6. **Prerequisites**: blocking checks (e.g., "verify `.adlc/context/project-overview.md` exists")
7. **Instructions**: numbered steps, often with sub-steps and explicit bash for deterministic operations (each ```sh fenced block may be an independent shell — a shared shell function must be re-sourced from a partial in the same block that calls it; see "Partials")
8. **Quality checklist**: post-run self-check items

Skills are pure markdown — no code, no package dependencies. The harness loads them at invocation time and the model executes the instructions in-context. The text is written so Claude Code, Copilot CLI, Codex, Gemini CLI and Cursor read it the same way (REQ-666): no `$ARGUMENTS`, no `!` line but the ETHOS one, no harness home path, and a fallback at every agent dispatch.

**Companions (REQ-661).** A skill over the budget keeps its detail in companion files one level below the skill directory, `<skill>/references/*.md` (the Agent Skills layout; no nesting), and `/proceed` keeps its `proceed/phase*.md` files beside `SKILL.md` instead (one layout per skill). A `SKILL.md` plus its companions is a **skill unit**. Two contracts are in force:

- **Read-and-follow (load-bearing).** The step's heading (for `/spec`, its numbered sub-step's title) stays in `SKILL.md` at the step's old position, followed by one sentence: "Read `<companion>` and follow it before you continue.", a clause naming what the file holds, and "Nothing in this file replaces it." The companion is the only copy of the step: on a harness that honours the Agent Skills layout the agent reads it with its file tool when it reaches the pointer, so `SKILL.md` carries no summary that could be executed instead. A section moves whole, or a whole numbered sub-step of one, with its prose, fences and marker blocks. Under this contract: `spec/references/intake-source-read.md` (Step 1.4 step 3), `spec/references/retrieval-body-read.md` (Step 1.6 sub-step 7), `template-drift/references/drift-report.md` (Step 5), `template-drift/references/reconciliation.md` (Step 6), `proceed/phases-state.md` (Pipeline State Tracking), `proceed/phases-telemetry.md` (Run-outcome telemetry), `proceed/phase-0-setup.md` (Step 0), `sprint/references/exec-engine.md` (the exec engine, REQ-659) and `proceed/phases-lite.md`, whose sections `SKILL.md` tells the agent to run.
- **Summary plus companion (documentation-only marker).** `proceed/phases-1-3-validation.md`, `proceed/phase-4-implementation.md` and `proceed/phases-6-8-ship.md`, each named by a `<!-- companion: … -->` marker under the phase heading, as described under the pipeline shape below.

A companion is read with a file tool and never preprocessed, so the preprocessing Claude Code applies to `SKILL.md` stays there: a fence or sentence that consumes the skill argument (the `'<request>'` placeholder fences of `/spec` Step 1.4, `/manifest`'s `'<req-ids>'`) and the ETHOS `!` line never move (`companion-templating`, `ethos-line`). `tools/lint-skills` walks every companion with the per-file checks a `SKILL.md` gets, treats the unit as one scope for the cross-fence checks and `canonical-helper`, and keeps its per-root site lists pointing at the file that holds each block. A reference by skill and step name ("`/proceed` Step 0 item 4") stays valid because the heading stays; a reference that named the file a section left names its new file.

## Agent anatomy

Agents live in `agents/<agent-name>.md` and have frontmatter declaring:
- `name` — identifier used when dispatching. Claude Code registers it bare on the symlink route and as `adlc:<name>` on the plugin route (REQ-669 ADR-6), so every dispatching step carries conventions.md's canonical dispatch paragraph
- `description` — tells the parent agent when to use this one
- `tools` — explicit allowlist (or `*` for general-purpose agents)
- `model` — optional override (e.g., `sonnet`, `haiku`) for cost/speed tuning

Agent bodies contain specialized instructions: role, focus areas, reporting format. The `/review` and `/proceed` skills dispatch multiple review-style agents in parallel (correctness-reviewer, quality-reviewer, architecture-reviewer, test-auditor, security-auditor, reflector).

An agent body is also a **checklist** the model can run itself. `/init` vendors every `agents/*.md` into the project's `.adlc/agents/` (REQ-666 BR-8), and the dispatch paragraph's inline arm reads it there when the harness cannot run subagents or the skill is already inside one: a harness whose reads are jailed to the session root, and a Claude Code subagent in a worktree, cannot reach ToolkitRoot. When `.adlc/agents/` is absent the arm names `/init` and reads `$ADLC_TOOLKIT_ROOT/agents/<name>.md`. `.adlc/agents/` is a checklist store, never an agent registry: no harness is configured to discover agents there. An inline review or audit is read-only. `/template-drift` reports the copies as the `agents` surface, and the lane check blocks `.adlc/agents/**` by default.

## Template anatomy

Templates at `templates/*.md` are the canonical shape for each artifact type:

- `requirement-template.md` — REQ specs (id, title, status, deployable, dates; Description, System Model, Business Rules, Acceptance Criteria, etc.)
- `task-template.md` — implementation tasks (id, title, req, status, dependencies)
- `bug-template.md` — bug reports (id, title, status, severity, dates; Description, Reproduction, Root Cause, Resolution)
- `lesson-template.md` — lessons learned (id, title, component, domain, stack, concerns, tags, req, created, updated, kind, evidence, confidence, enforcement, generalizes, supersedes). The last six are the REQ-646 v2 attribution fields; `kind`, `evidence` and `confidence` are required on every lesson a capture step writes, and `enforcement`, `generalizes` and `supersedes` are optional. See "Knowledge retrieval" below.
- `assumption-template.md` — validated-assumption knowledge entries
- `taxonomy-template.md` — tag/taxonomy reference used by the retrieval tagging

The `templates/` directory is authoritative for the full set (it also carries the non-`.md` `config-template.yml`, `permissions.yml` and `hooks.yml`, and the instruction-file bodies under `templates/instructions/`); the list above describes the per-artifact `*.md` templates and may lag the directory — prefer `ls templates/` when an exact roster matters.

Templates are copied into consumer projects by `/init` (into `.adlc/templates/`). Consumer projects may customize their local copies; `/template-drift` detects divergence from the canonical set.

## Partials

Partials at `partials/*.sh` are small POSIX shell snippets shared by multiple SKILL.md files. Skills source them from shell fences with a two-level fallback: the consumer project's vendored copy under `.adlc/partials/` first, then the installed toolkit's copy under ToolkitRoot (`$ADLC_TOOLKIT_ROOT/partials/<name>.sh`, see "Install routes" below), so the pattern works whether or not `/init` has copied the partials into the consumer repo. The ETHOS `!` line, the one preamble line a skill keeps, does not reach the toolkit copy at all: it names no path outside the session root (BUG-218; conventions.md "Ethos injection pattern"). The `/init` skill copies `partials/*.sh` into `.adlc/partials/` alongside `templates/`. A partial that itself needs a toolkit-owned file reads it through the default-expansion spelling `"${ADLC_TOOLKIT_ROOT:-$HOME/.claude/skills}/…"`, because a partial carries no root line and may be sourced by an older SKILL.md text or a test harness with the variable unset (REQ-669 ADR-2). Keep partials trivially auditable: one snippet per file, no aggregator (`lib.sh`) until there are more than five.

A sourceable partial is also the **only** sanctioned mechanism for sharing a shell *function* across steps, because SKILL.md fenced blocks do not share shell state across steps — each may be an independent shell invocation, so a function defined in one fenced block is undefined in another (the silent telemetry-loss class — REQ-436, REQ-428). A shared function (e.g. `_adlc_emit_step_telemetry` in `partials/emit-step-telemetry.sh`, alongside the `delegate-gate.sh` precedent) must be re-sourced at *each* call site in the same fenced block as its invocation, in one canonical guarded spelling, after the fence's ToolkitRoot root line — `if [ -f .adlc/partials/<name>.sh ]; then . .adlc/partials/<name>.sh; else . "$ADLC_TOOLKIT_ROOT/partials/<name>.sh"; fi`. REQ-669 changed only the `else` operand; the REQ-610 operand `~/.claude/skills/partials/<name>.sh` is retired and is now a finding. `.` is a POSIX special built-in, so a failed source is fatal under `sh`; the repo-local copy is therefore tested with `[ -f ]` before it is sourced, and never guessed at with `||` (REQ-610). Both invariants are enforced structurally rather than by prose (LESSON-012): the `tools/lint-skills` `cross-fence-fn` check flags any function defined in one fence but called from a different fenced block, and its `unguarded-source` check flags any other spelling of the two-level source. Its `toolkit-root-line` check requires the canonical root line, byte-exact, above the first `$ADLC_TOOLKIT_ROOT` read in every fence, and `no-harness-path` (REQ-666, which absorbed REQ-669's `toolkit-path`) flags a literal harness home path: any of the five harnesses' homes in skill, agent and partial-doc text, and a toolkit (`~/.claude/skills`, `~/.claude/agents`) or foreign-harness path in code, outside its one exception list. See conventions.md "Bash in skills" for the call-site rule.

## ADLC pipeline shape (consumer-project view)

When a consumer project runs `/proceed REQ-xxx`, the pipeline phases are:

```
/validate (spec)
   ↓
/architect  ← creates .adlc/specs/REQ-xxx/tasks/TASK-yyy.md
   ↓
/validate (architecture + tasks)
   ↓
Implement (parallel task-implementer agents)
   ↓
/verify (reflector + 5 reviewer agents in parallel)
   ↓
/review findings fixed in single pass
   ↓
Create PR
   ↓
PR cleanup + CI
   ↓
/wrapup (merge, artifact updates, knowledge capture, deploy)
```

Each phase has a validation gate. Failed validation loops up to 3 times before pausing for human input.

**The lite lane (REQ-652)** is the same pipeline branched by the spec's `lane` value, not a second pipeline:

```
/spec (Step 1.7 triage → lane: "lite")
   ↓
/proceed Step 0 (status approved; Phases 1–3 recorded skipped)
   ↓
Implement from the acceptance criteria (fresh retrieval, no task files) → gates
   ↓
lite-reviewer (one pass) → fixes → LANE CHECK
   ↓                                  │ crossed a line, a reversal, an implementer finding, or --full
Create PR → PR cleanup + CI (+ lane check) → lane check → merge → /wrapup
                                      ↓
                    escalate: spec lane "full" + lane_escalated, resume at /validate (spec)
                    on the same branch, worktree and PR
```

`proceed/SKILL.md` keeps Phase 5 (Verify, with the delegate pre-pass gate) inline. Since REQ-661, Step 0, Pipeline State Tracking (the state schema and the Gate Protocol) and Run-outcome telemetry live in read-and-follow companions (`proceed/phase-0-setup.md`, `proceed/phases-state.md`, `proceed/phases-telemetry.md`; see "Companions" under Skill anatomy), and the thinner phases are extracted to companion files referenced via `<!-- companion: <path> -->` markers in SKILL.md:

- `proceed/phases-1-3-validation.md` — Phases 1–3 (spec validation, architect, architecture/tasks validation)
- `proceed/phase-4-implementation.md` — Phase 4 (implement)
- `proceed/phases-6-8-ship.md` — Phases 6–8 (PR creation, cleanup/CI, wrapup/merge)
- `proceed/phases-lite.md` — the lite lane (REQ-652): Step 0 additions, Phases 4 and 5 on the lite lane, the lane check, escalation, and the lite PR body

The companion marker is documentation-only — Claude Code does not auto-load referenced files. SKILL.md's inline summary is sufficient to execute each extracted phase; the companion holds the full step list for maintainers and for in-depth reference. `phases-lite.md` is the exception among the four: `SKILL.md` tells the agent to run its sections, so it is read-and-follow. Phase 5 is intentionally not extracted (ADR-3 of REQ-416, kept by REQ-661 OQ-1) because the delegate pre-pass gate-handoff is load-bearing.

## Workflow engine

Some orchestration is too dispatch-heavy for a single subagent (a subagent cannot nest further subagents). For those cases the toolkit ships **deterministic Dynamic Workflow scripts** under `workflows/` — a JS orchestration script plus the JSON-Schema literals it validates agent output against. Scripts are read from the installed toolkit on either route (`$ADLC_TOOLKIT_ROOT/workflows/<name>.workflow.js`) and `/init` vendors them into a consumer's `.adlc/workflows/` alongside `templates/` and `partials/`. A skill resolves a script with the same **two-level fallback** used everywhere else — consumer copy first (`.adlc/workflows/<name>.workflow.js`), ToolkitRoot's copy as fallback — so it works whether or not `/init` has run. The script names agents in code, so `/sprint` passes `args.agentNamespace` (`"adlc:"` on the plugin route, `""` on the symlink route) and every `agentType` goes through the pure `agentTypeFor(name, ns)` (REQ-669 ADR-6).

**Agents are leaves; the script is the orchestrator.** The Workflow primitive has no shell or filesystem of its own, so every git/gh/file/state operation runs *inside* an `agent()` call; the script owns only control flow (sequence, fan-out, loops, merge ordering). This is the model that dissolves the "a subagent can't dispatch subagents" constraint: the script dispatches the leaves and parallelizes the read/report phases that pay for fan-out while serializing the single writer.

**`/sprint` is a three-engine dispatcher.** It selects the **workflow** engine only when the `Workflow` tool is actually invocable in the session **and** the run opts in (`--workflow`, or once the engine graduates to default); otherwise it uses the **legacy** background-runner engine with no behavior change. Dynamic Workflows is a research-preview, plan-gated capability that can be absent (headless/cron runs, non-qualifying plans), so the legacy engine is an always-available, unchanged fallback — the dispatcher degrades to it (with an explicit notice) rather than failing when the workflow engine is requested but unavailable. The **exec engine** (REQ-659) is selected only by `--exec`, and is never a default or a fallback.

**The exec engine: the orchestrator is a program.** `adlc sprint-exec` (`tools/adlc/sprint_exec.py`, stdlib only) is a foreground supervisor plus clients over a Unix socket, so every operation works from a plain shell. Per REQ it prepares a working copy by the adapter's declared strategy, builds the prompt itself, launches one headless harness per REQ with the prompt on stdin, and reads what comes back as data. The model runs Phases 0 to 7 and stops at the merge gate; merge, deploy, the close-out merge and cleanup are the program's, after an operator's `approve`. **Prompt ownership:** `exec_prompt.py` assembles the bytes from ToolkitRoot and the primary path, never a working copy. Each excision and rewrite is anchored and must match exactly once, and a final scan of the delivered bytes refuses any merge instruction, so a skill edit that moves a sentence stops the launch rather than reaching an unattended model. **Per-run trust:** `exec.trust_grant` says what the engine does per run, which is not always what the harness's top-level `trust` says it reads: `claude` declares `none`, because both tiers go on the command line and a linked worktree resolves Claude's trust at the main repo root, so a per-working-copy entry would be inert (ADR-5). **What is structural (Rule B):** not the allow and deny lists, which are defense in depth with declared residuals, but the approval ledger in a random 0700 run directory outside every tree, a one-time token whose digest only the supervisor's memory holds, a merge pinned with `--match-head-commit` to the head the operator saw, a trial merge and rebase in an orchestrator-owned detached worktree, local `--no-renames` diff gates, scoped child credentials, branch protection, and the exit checks (ancestry, patch-id, first-parent). The orchestrator runs nothing a harness could write: partials resolve from the install by absolute path, git is neutralized through the environment because partials spawn it themselves, and a sha256 manifest of the install and resolved binaries plus a checksum of the common gitdir are verified before each exec. See `.adlc/specs/REQ-659-sprint-exec-engine/architecture.md`.

**State has two layers.** The durable `pipeline-state.json` remains the cross-tool artifact that `/status` and the legacy engine read and that survives across sessions; the workflow **journal** is the in-run cache that powers `resumeFromRunId` (answer-a-halt-and-relaunch) within a single workflow run. They serve different layers and neither replaces the other — keeping `pipeline-state.json` is what lets `/status` and the legacy path keep working unchanged.

**The workflow engine has no lite lane (REQ-652 ADR-11).** Its phases are a fixed script, so it runs a lite REQ on the full lane, logs one line per such REQ (`liteFallbackNotice`, in the script's pure block), and writes no `lane` object to state, so `/status`'s Active Pipelines column shows what actually ran (the Requirements Summary still shows the spec's lane). Both engines treat a `draft` lite REQ as eligible, since a lite REQ skips spec validation by design. The legacy engine follows the lite lane through `pipeline-runner` running `/proceed`.

## Knowledge retrieval (current and evolving)

Skills retrieve relevant prior knowledge at context-loading time. `/spec` Step 1.6 is the **weighted-score retriever** that REQ-258 introduced. It reads the frontmatter of every candidate in three corpora: `.adlc/knowledge/lessons/`, `.adlc/specs/*/requirement.md` (an exclusion filter on `status`, BUG-194) and `.adlc/bugs/` (`resolved` or `closed` only). It scores each candidate against the Step 1.5 query: `+3` for the same component, `+2` for the same domain, `+2` per shared concern, `+1` per shared stack entry or tag, and a `+1` floor for an untagged lesson. It drops zero scores and keeps the **top 15 pooled across all three corpora**, with no per-corpus quota. `/review` Step 1 runs its own lesson-only relevance filter (component, domain plus component prefix, or tag), tops it up by recency when fewer than 5 lessons match, and caps it at 15. `/architect` greps lesson frontmatter for the affected component or domain, and so does the `reflector` agent when its caller supplies no set (`/reflect`).

**Retrieval by surface, after the spec (REQ-647).** A spec's `## Retrieved Context` is frozen when the spec is written (LESSON-604), so the later phases retrieve again, by the surface they touch. One engine, `tools/adlc/lessons.py`, behind one partial, `partials/lessons.sh` (`adlc_lessons select|text|log-line|ack-check`), serves every call site: `/proceed` Step 0 (`step0`: the REQ's own tags, top 10), each Phase-4 task (`task`: the components of the task's files plus their ancestors, top 5, then up to 3 lessons newer than the spec with the most specific component first, then the Step-0 set's `kind: process` lessons, never past 15), Phase 5 (`phase5`: the diff's components, top 15, topped up to 10 when fewer than 5 score), `/bugfix` Phase 2 (`bugfix`: top 5), and the sprint workflow engine's three retrieval leaves. The model supplies only the path → component inference (`/review` Step 1 item 7a); scoring is the `/spec` Step 1.6 rule over lessons, and each lesson loads as its frontmatter, `## Lesson` and `## Applies When`, capped at 40 lines. The implementer acknowledges an applied lesson with a `Lessons:` commit trailer or in its task's `## Verification` block, and Phase 5 Step B lists the applicable lessons nobody acknowledged as Info findings that never block. Each set is recorded, without its text, in the additive `pipeline-state.json.lessons` of the primary-path copy, which nothing reads for control flow. Retrieval is never a gate: an unavailable engine is one logged `lessons: unavailable — <reason>` line and the phase continues. In the workflow engine a finding's `lessonId` escalates only when it is an id in the Phase-5 set the panel was handed. `/spec`'s and `/architect`'s own retrieval, and the lite lane's fresh retrieval, are unchanged.

**Lesson schema v2 (REQ-646).** `templates/lesson-template.md` carries six attribution fields after the retrieval tags. They were added without changing any existing field, so every lesson already in the corpus parses unchanged, because readers match keys by name. `kind` (`process` or `domain`), `evidence` and `confidence` (`high`, `medium` or `low`) are required on every lesson a capture step writes. `evidence` must contain a citation token: a commit sha, a `BUG-`/`REQ-`/`LESSON-`/`TASK-` id, a `path:line`, or a test name. `confidence` depends on whether the evidence contains a contrast, such as a bug reproduced and then fixed or a test that failed and then passed. `enforcement` (`none`, `lint:<check-id>`, `test:<path>`, `script:<path>` or `hook:<name>`; absent means `none`), `generalizes` and `supersedes` (lists of lesson ids) are optional. `templates/taxonomy-template.md` documents the three enums. Existing lessons are not backfilled. A lesson without the fields reads as "not stated", never as `confidence: low`.

**`confidence`, `supersedes` and `kind` have readers.** `/review` Step 4 does not escalate a finding's severity when the matched lesson has `confidence: low` or is named in another lesson's `supersedes`. It still cites the lesson, with a `— not escalated` annotation. A legacy lesson with no `confidence` escalates as before. `/spec` Step 1.6 marks a retrieved lesson that another lesson supersedes as `superseded by LESSON-yyy`, in its retrieval summary and in `## Retrieved Context`, and leaves its score and rank unchanged. Both skills find the superseding lesson with a corpus-wide reverse lookup, because it is usually not among the lessons already retrieved. The lookup reads only each lesson's frontmatter for a `supersedes:` line naming `LESSON-<id>`, and the id is checked against `^LESSON-[0-9]{3,6}$` before it is used. `/review` runs the lookup lazily, only for a lesson a finding matched. It also ignores the `confidence` and `supersedes` of any lesson file that the diff under review adds or modifies, so a change cannot switch off its own escalation. `kind` is read by REQ-647: a `kind: process` lesson in the Step-0 set is carried into every task's set, and qualifies for the Phase-5 acknowledgement check whatever its component; an absent `kind` qualifies for neither. No retrieval or review step reads `evidence`, `enforcement` or `generalizes` yet. Readers for `enforcement` and `generalizes`, and any scoring change based on `confidence` or `supersedes`, are out of scope for REQ-646.

**Finding the transcript (BUG-253, REQ-660).** `/wrapup` Step 4 drafts a lesson from the session's own transcript, and the only proof that a file is that transcript is a mark the run printed itself: an id proves a file mentions the work, not that it is the run (LESSON-733). `adlc_transcript_find` tries a three-rung chain and accepts only a file holding the mark on each: the `.adlc/.session/*` sidecars the `session-record` hook writes, then the Claude, Codex, Copilot and Gemini roots (Cursor is sidecar-only), then Fallback drafting from the conversation. One holder wins; none or several refuses. `extract-chat --format` parses a format only when a real captured transcript proves its shape, and today that is `claude`. See `.adlc/specs/REQ-660-session-sidecar-and-multi-harness-transcripts/architecture.md`.

**Capture and the writer-side guard.** `/wrapup` Step 4 and `/bugfix` Phase 6 Step 4 are the only writers of `LESSON-*` files. Both carry the same four capture rules, byte for byte: declare `kind`, cite the moment in `evidence`, choose `confidence` by contrast, and treat `NO_ENTRY` as a valid answer. Each capture step reports its outcome in the `### Lessons captured` slot of the skill's summary, either as one `LESSON-xxx` line per lesson written or as exactly one `NO_ENTRY: <reason>` line. A rule-3 `NO_ENTRY` (nothing transferable survived) allocates no id and writes no file. A repair-loop `NO_ENTRY` (below) comes after allocation, so it consumes its id and leaves a gap in the counter. Every write is checked by `partials/lesson-check.sh`, whose `adlc_lesson_check <path>` validates the file just written and returns **0** (pass), **1** (violations, one `<field>: <reason>` line each on stderr) or **2** (usage: missing argument, unreadable file, no frontmatter block, a symlink, or a basename that is not `LESSON-<digits>-<slug>.md`). It checks the required keys, the enums, the lesson-id lists, the citation token in `evidence`, and the `## Lesson` and `## Applies When` sections. It rejects a home-directory path in `evidence` or `enforcement`, and a credential-shaped string in the title or any of the six new fields. It also rejects, at parse level, a value its one-line reader cannot read: an opening quote that is never closed, a value continued onto the next line (such as a block list), and a key given twice. Key spelling fails closed: a key not written exactly as `key:` followed by a blank (`supersedes:[…]`, `kind:process`) is a violation on that key, not a silently unset field. On rc 1 the drafter repairs only what the check named, either a frontmatter field or one missing or empty section, and runs the check again, at most twice. After a third failure the drafter deletes the draft and records `NO_ENTRY: schema check failed — <field>`. That outcome is not a pipeline halt. The check never runs over the historical corpus. `partials/lesson-check.md` holds the return-code contract and the rule table. The `tools/lint-skills` `lesson-check-order` check enforces the structure of both SKILL.md files. It checks the fence order (the `lesson-write-point` marker, then the `adlc_lesson_check` fence, then the `adlc_recheck_id lesson` fence). It checks that the two skills' capture-rule blocks are byte-identical, and that every rule line appears in `/wrapup`'s delegated `--question`.

## Key cross-cutting dependencies

It is a maintainer tool, run from a clone (it reads git objects at a commit on `main`, so the plugin's cache copy cannot run it), and nothing in a skill, `adlc doctor` or `install.sh` calls it. Two consequences for other work: a REQ that adds a new kind of file under `.adlc/`, or frontmatter the strict recognizer in `frontmatter.py` rejects, fails the `tools/dataset` current-tree tests until `classify.py` names it; and `tools/adlc/credential_redact.py` is a third copy of the credential chains in `partials/intake.sh` and `partials/lesson-check.sh`, pinned to both by `tools/adlc/tests/test_credential_redact.py`, so an edit to either shell regex must update it. The Hub client (`huggingface_hub`) is imported only inside `tools/dataset/publish.py`, and pinned only in `tools/dataset/requirements.txt`. See `tools/dataset/README.md`.
- **Forge adapter (REQ-520)**: `partials/forge.sh` is the single home of `gh`/`az` PR-lifecycle commands — a sourceable partial exposing `adlc_forge_pr_{create,ready,edit,view,list,merge,comment}` with GitHub (`gh`) and Azure DevOps (`az repos`) backends and an `ADLC_FORGE_MOCK=1` offline fixture backend. Provider resolution (per-project `.adlc/config.yml` `forge.provider` > machine config > `auto` origin-URL detection, fail-loud on unrecognized host) and the key-shaped-`auth` refusal live in `tools/adlc/forge_config.py` (a thin flat-YAML reader mirroring `parse_delegate_config` — no shell YAML parsing, REQ-515 ADR-3). Every PR-lifecycle call site in `/proceed`, `/architect`, `/manifest`, `/bugfix`, `/wrapup`, `/sprint`, and the sprint workflow routes through the adapter; `tools/lint-skills`'s `forge-direct-gh` check rejects new direct `gh pr <op>` in skill fences. The GitHub backend is byte-compatible with the prior direct calls (zero change for GitHub installs). `adlc doctor`'s `forge` check (in `tools/adlc/checks.py`) **supersedes** the former standalone `gh-auth` check — it resolves the provider and probes the right backend's CLI + auth + a read-only API probe, SKIP-with-reason on a remote-less repo. `gh pr diff`/`gh pr checks` (CI polling is out of scope) and the REQ-518 `id-alloc`/`id-recheck` `gh api` tree reads (BR-8 pure-git merged-artifact scan, not a PR op) stay direct.
- **Hugging Face Space (REQ-670)**: `space/` is a static Space (`sdk: static`) that runs `/spec` intake in the visitor's browser. The browser calls the Anthropic Messages API directly with the visitor's own key and the `anthropic-dangerous-direct-browser-access` header, so the key never reaches a server process. A meta CSP limits `connect-src` to the Space and `api.anthropic.com`. Every rule lives in the pure `space/intake.js`: the budget, the redaction, one forced `record_intake` tool call, output validation, and the five BR-10 error classes, with `unclassified` as the default. `space/app.js` renders with `textContent` only and never touches storage or the console. The maintainer deploys it from a tagged release (`RELEASING.md`).

## Delegation opt-in: the gate may veto, only Python may authorize

The delegation opt-in predicate has exactly **one** implementation —
`_common.resolve_gate_verdict()`. `partials/delegate-gate.sh` may *withhold*
delegation (`no-binary`, and the `ADLC_DISABLE_DELEGATE` veto) but may never
*grant* it.

The distinction is not stylistic. A **veto** arm can only return *disabled*, so
duplicating one across layers is redundancy — the copies agree or abstain, never
contradict. An **authorizing** arm can return *enabled*, so a stale copy grants
what the real resolver would refuse. `delegate-gate.sh` is vendored per repo,
which makes it the wrong home for any authorizing decision.

That invariant has already been violated from both directions:

- **BUG-205** — the config arm was a shell fast path; correct for `enabled: true`,
  wrong for `enabled: false`, and an operator's written opt-out was silently
  overridden while file contents were transmitted.
- **BUG-209** — `ADLC_DISABLE_DELEGATE` existed in shell and nowhere in Python, so
  both CLIs ignored the documented emergency stop entirely.

REQ-603 consolidated the authorizing arms and kept the veto duplicated under a
stated condition: Python must recognise at least every input the shell does,
enforced by `tools/delegate/tests/test_cross_layer_veto.py`.

**Both sides of that authority are hardened by REQ-609.** Making Python the sole
authority made its config reader the sole authority, and that reader was a
hand-written flat scanner that **skipped** what it did not understand — nine
distinct fail-opens, six of them added by the pass that tried to fix it. The
opt-in config is now parsed by PyYAML (`yaml.safe_load`, a loader that raises on a
repeated key) behind a **strict, closed schema**, in one loader —
`tools/delegate/_machine_config.py` — that returns exactly `absent`, `parsed`, or
`malformed` and never raises. `tools/delegate/_common.py` and
`tools/adlc/forge_config.py` are both adapters over it, so a multi-section config
cannot lock out one consumer by the other's rule, and a differential oracle
compares the adapter against `yaml.safe_load` itself over a seeded and a generated
corpus, so the suite is no longer bounded by one author's imagination. A recognizer
refuses what it does not understand; there is no skipped line left to fail open on.
On the shell side, binary resolution asks the **filesystem** — a `$PATH` walk over
absolute entries only — and never a lookup builtin, because any answer sourced from
the shell's own machinery inherits every table that machinery consults (a `hash -p`
entry defeated REQ-603's bare-name rejection). REQ-515 ADR-3's "no PyYAML for three
scalar fields" is **amended by REQ-609**: those three scalars now gate exfiltration.
