## Description

This is the adapter half of the exec-engine phase of
`.adlc/research/multi-harness-plan.md` (revision 2; the plan's P6b). The exec
engine core (REQ-659, specified in parallel) gives `/sprint` a third engine: a
shell orchestrator that prepares a working copy per REQ, builds the whole
prompt itself, launches a harness non-interactively with the routine-tier
allowlist, halts at the merge gate by reading `awaiting_approval` from
`pipeline-state.json`, and executes the one-way moves (merge, deploy, cleanup)
itself after `/sprint approve` (plan §2f, Rule B). REQ-659 defines the adapter
interface the engine calls — the `exec` sub-block of a harness adapter — and
ships it with Claude Code only.

This REQ makes that engine run on the four non-Claude harnesses by filling in
the **exec block** of each adapter file the REQ-656 (Copilot, Cursor), REQ-655
(Codex) and REQ-658 (Gemini) adapter REQs create under `harness/<name>.yml`.
Per harness the block declares seven things the engine cannot guess: the
launch command template with the prompt delivered on stdin; how the
routine-tier allow entries and the deny-tier entries (the one-way moves)
render into that harness's flags or pre-rendered files; how trust for the
working-copy path is written before launch and revoked after (using the
mechanism the adapter's top-level `trust` field already declares); how the
harness's JSON or streamed output is parsed into the final message and a
session id; the resume command; the map from the harness's exit codes to the
engine's closed vocabulary; and which working-copy strategy the harness needs
(plan §2f step 1) because a sandbox rooted at a linked worktree cannot reach
the common git dir (finding M5).

Every one of those seven is a claim about a third-party binary whose
behaviour the plan's survey took from vendor docs, and §6 lists the questions
docs could not answer. So an adapter's exec block is **not accepted on the
strength of its author's reading**: it is accepted only when every required REQ-664 probe
for that harness is acceptable, in `.adlc/research/harness-probes/<harness>.json`
for the harness version the adapter declares, for what the adapter declares
(ETHOS: verify, don't trust): the hard probes must read `pass`, and the
declaration-bound probes must read `pass` or `fail` with the declared value
agreeing with the verdict (BR-11). Until then the engine refuses to launch it,
and it recomputes that status from the result file at every launch. This REQ runs no experiment of its
own; it cites REQ-664's result file. The required probe ids per harness are
`git-write-worktree` (§6.1b, with `git-write-main` for §6.1a),
`trust-then-headless` and `session-start-context` (§6.8), `stdin-prompt`
(§6.12), `fence-vs-allowlist` (§6.11), `shell-timeout` (§6.6, against the
120 s `adlc-read` floor) and `ask-tier-deny` (§6.3) — the last required for
all four harnesses, not Cursor alone.

Because real binaries cannot run in CI, REQ-664's profile-driven fake harness
is extended with exec scenarios, one per adapter, so the engine's approval
protocol runs end to end against every adapter offline: launch, stdin prompt,
allow and deny rendering, trust write and revoke, `awaiting_approval`, approve
or reject, orchestrator-executed merge through the forge mock, resume, and
every mapped exit code. The README gains one exec section per harness stating
what the engine does on it and what is lost there (plan §4). (informed by
LESSON-619, LESSON-663, LESSON-718)

The allow and deny rendering in this REQ is spelling-level and is **not the
gate**. Rechecks of the Rule B specs found that allowlist and prefix-deny
semantics cannot be made a gate (allows that execute their arguments, `gh api`
and semantic equivalents reach the deny tier), and each round that closes
spellings exposes more. So this REQ carries the structural controls on the
adapter side (config surfaces, closed-world argv, the halt-time exec-path gate,
version-bound verification) and states the allowlist's limits as declared
residuals (BR-19); REQ-659's structural halt is the gate.

| run_resumed | approval granted and model work remains | harness, session_id, argv |

## Business Rules

- [ ] BR-1: Each of `harness/copilot.yml`, `harness/codex.yml`, `harness/gemini.yml` and `harness/cursor.yml` gains an `exec` block whose shape is the ExecBlock entity, validated by the REQ-657 adapter loader against a closed schema. This REQ extends the opaque `exec` sub-block REQ-657 declares (REQ-659 owns the engine keys, this REQ the per-harness adapter keys) with a schema-version bump; `harness/claude.yml`'s exec block (REQ-659 BR-3) is migrated mechanically to the widened shape in the same change so it loads, and its engine behaviour is unchanged (REQ-659's ACs re-run). An unknown key, a missing required key, a wrong type, or an exit map without `0: ok` refuses the **whole adapter** with the key named, never a partial load. An adapter without an `exec` block is not exec-capable, and the exec engine refuses it by name. The BR-11 gate and the `status` and `probes` keys apply to the four harnesses; the migrated `claude` block carries `status: verified` on REQ-659's own evidence (its `claude.json` rows), not on a probe run this REQ adds. (informed by LESSON-614, LESSON-716, LESSON-471)
- [ ] BR-2: The launch command is an argv template, never a shell string, and the prompt is delivered on stdin in every case. Placeholders are substituted as whole tokens, never by shell interpolation. The templates follow the plan's §2f table: Copilot `copilot -s --output-format json --no-ask-user --trust-folder --allow-tool … --deny-tool … -C <wt>` with **no `-p`**; Codex `codex exec --sandbox workspace-write -C <wt> --output-schema … -o …`; Gemini `gemini --output-format json` with allow and deny read from the `.gemini/settings.json` rendered into the working copy (BR-3); Cursor `agent -p --output-format json --workspace <wt> --trust`. The forbidden-flag vocabulary is the adapter's `forbidden_flags` list (REQ-659 BR-8), seeded by the engine with REQ-659's six tokens (`--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--permission-mode bypassPermissions`, `--yolo`, `--force`, `--allow-all`) and extended per harness here: Codex `--full-auto`, `--dangerously-bypass-approvals-and-sandbox`, `danger-full-access`, `--ask-for-approval never`; Copilot `--allow-all-tools`; Gemini `--approval-mode=yolo`; Codex also forbids every `-c`/`--config`/`-p`/`--profile` token absent from its template (BR-16); Cursor none beyond the seed. Each forbidden entry is matched as a contiguous token subsequence of the argv after splitting any `--flag=value` token at the first `=` (so `--approval-mode=yolo` and `--approval-mode yolo` both match, as do `--ask-for-approval=never` and `--ask-for-approval never`), never as a glob. The orchestrator applies the same matcher to the final argv at launch and at resume. The `exec-no-bypass` lint reads that list and fails on any of its entries in `launch`, `resume` or a rendered argv fixture. `forbidden_flags` is a lint backstop; the closed-world argv check of BR-16 is the control. (informed by LESSON-663, LESSON-012, LESSON-619)
- [ ] BR-3: The `routine` tier of `templates/permissions.yml` is rendered through the REQ-657 allowlist renderer at `exec` scope into the harness's allow form (`--allow-tool` flags, a pre-rendered Codex rules file, the `.gemini/settings.json` REQ-658 renders into the working copy, or Cursor's two rules files, both as REQ-656 BR-8 renders them), including the broad partial-sourcing fence entry and both `git` and `git -C` spellings (plan §2e), except that a routine allow that is a proper prefix of, or can wrap, a deny-tier spelling (including `git -C <path>`) is omitted at every scope including `exec`. A wrapper allow is restored only for the `git-c` shape, when REQ-664's `wrapped-allow` variant (which denies the plain spelling and asks the wrapped one), with its dedicated `allow-only-git-c` and `baseline-git-c` controls, is `pass` at the adapter's `harness_version` (REQ-657's `deny_under_allow` entry for that shape); `env-prefix` and `shell-opener` allows remain omitted, those shapes staying `unverified`. An omission is a finding in the `allowlist-fidelity` report and is declared in `accepted_fidelity` like any other loss; this REQ adds no second renderer — for Gemini in particular the exec adapter declares `allow_render: file` and reuses REQ-658's settings-file render rather than spelling `--allowed-tools` flags — and spells no entry itself. The exec render of `.gemini/settings.json` and `.codex/config.toml` is the full project render plus the exec routine tier, so hooks and `context.fileName` are kept, and the `session-start-context` probe runs against that exact file. Allow matching is spelling-level and a declared residual (BR-19). The adapter's `accepted_fidelity` map (REQ-657) is the source of the expected losses per harness; the renderer's `allowlist-fidelity` report for each run is attached to the run log so the granularity lost on Cursor and Gemini is visible per run, not only in the README, and the pre-flight compares the run's findings against `accepted_fidelity` at `exec` scope (REQ-657 BR-8), where `fence.partial-source`'s `widened` verdict is the expected finding and not a loss; a loss not declared there fails the run's pre-flight.
- [ ] BR-4: The `deny` tier (the one-way moves) is rendered as a hard **deny** wherever the harness can express it (Copilot `--deny-tool`, Codex `decision="forbidden"`, Gemini policy deny, Cursor `deny`); the exec engine renders the deny tier as a hard deny on every harness whose `capabilities.deny` is `yes`, including those whose interactive render is `confirm` or `unsupported` (REQ-657: `exec.deny_render` is keyed on `capabilities.deny`, independent of `deny_tier_render`). Deny is a one-way convenience and never the gate: the gate is REQ-659's `awaiting_approval` halt, and the prompt the engine builds still instructs the model to stop at the merge gate regardless of deny. Because file-rendered rules live in a working copy the model can write, rule files are re-rendered from `templates/permissions.yml` and checksum-verified immediately before launch and before resume; a mismatch there is logged and overwritten, never trusted, and the same checksums are re-verified at exit and at the halt (BR-15). User-level placement is restricted to the deny tier (Codex `~/.codex/rules`, Gemini policy): the allow tier is never rendered at user level, and exec never overwrites operator content in a user-level policy file. The ExecBlock's `user_policy_file` names a separate toolkit-owned file (Gemini `adlc-exec-deny.<ext>`; Codex `adlc-exec.rules`), written whole-file and atomically, under the trust-file serialization (BR-5), by `adlc harness install --exec` or the pre-flight and never by the model. A directory manifest of the policy folder is checked at launch and resume, and the run is refused if the file is missing, has drifted or a stray file appears. Because the file lives in user config it persists across runs and projects and applies to the operator's own sessions, which the README states (BR-14). The rendered deny set is at minimum a superset of today's ask-tier set plus `engine_deny`. A `deny`-tier entry a harness cannot deny (including an `engine_deny` entry that cannot be spelled) carries the renderer's `deny-unsupported` verdict, is raised and logged per run as `deny_unsupported` and is named in that harness's README section; it never silently downgrades to allowed. On every harness each `deny_unsupported` entry yields a loud pre-flight line. The run is refused when the entry is a local destructive move (`reset --hard`, `clean -f`, `branch -D`, `rm`, `release`), or when `sprint.exec.require_branch_protection` is set and protection is not `protected`. Under `--allow-unverified` with `ask-tier-deny` not `pass`, the whole deny tier is treated as `deny_unsupported`. A file the engine renders at `exec` scope is never part of the REQ's PR and is guarded by the halt-time PR-diff gate (BR-17). Exec-scope files are whole-file overwrites and the whole file is checksummed. Every adapter's deny is accepted only on the `ask-tier-deny` probe (§6.3): `deny_render: flags` or `file` requires the probe's `deny-under-allow` variant (and `wrapped-allow` for wrapper shapes) to read `pass` for the deny-tier entries it covers, and a `fail` requires `deny_render: none` (BR-11). The probe's own status is the disjunction over its `lone-deny`, `deny-under-allow` and `wrapped-allow` variants, with `baseline` and `allow-only` as controls outside that disjunction, recording that the deny held without a bypass flag and what a denied command produced. (informed by LESSON-663)
- [ ] BR-5: Trust is per run and surgical, using the mechanism the adapter's REQ-657 top-level `trust` field declares (REQ-659 BR-5 reads the same field). For Codex (`user-config-entry`) the engine writes `[projects."<wt>"] trust_level = "trusted"` into the user config before launch; for Gemini (`trusted-folders-file`) it appends the path to `trustedFolders.json`; Copilot and Cursor (`flag`) get the flag and need no revoke. The path must be absolute and resolve under the run's working-copy root, validated on the resolved value before any write (a relative path, a symlink escaping the root, or an empty value refuses). The write is additive: every other entry in the file is byte-identical afterwards, and an entry that already trusted the path is recorded `pre_existing` and left alone on revoke. Revoke removes exactly the entry this run wrote and runs on success, failure and abort through REQ-659's cleanup path (BR-5, BR-20). Writes to the shared user file by concurrent sprint runs are serialized by the orchestrator. A REQ-664 probe run must not run concurrently with an exec run on the same machine, because both edit the same trust file; the orchestrator refuses to launch while REQ-664's recovery marker exists. Trust is accepted only after the `trust-then-headless` and `session-start-context` probes (§6.8) read `pass`: a headless run started immediately after the write honours it and the session-start hook context reaches the model. (informed by LESSON-471, LESSON-718)
- [ ] BR-6: The output parser is strict and orchestrator-side. For each adapter it extracts the final assistant message and the session id from the declared output format and source using the declared path expressions; any shape it does not recognise, a truncated stream, or an empty final message yields a parse failure — `exec.exitClass: error` with the parser's message written to `notes` (REQ-659 BR-15's failure-message slot); no `reason` key is added to `exec` — never `ok`. ## Assumptions

- REQ-659 defines the exec interface this REQ fills (one `exec` block per adapter) and the exec engine's state fields. This REQ adds no state field of its own; it populates REQ-659's additive `exec.exitCode` and `exec.exitClass` (BR-21) through each adapter's `exit_codes` map, and `denied` sets REQ-659's `status: blocked` with the last message in `blockers`. It changes no approval semantics.
- The flag names and output formats are the plan's docs-verified survey of 2026-10-27; each REQ-664 result records the harness version it ran against, because the flags can drift between releases, and an adapter is `verified` only for that version.
- A headless ask is a deny on Copilot, Codex and Gemini, and Cursor approves unless denied; the exit code or state a deny produces is what the `ask-tier-deny` probe records, not what this spec presumes.
- Gemini CLI remains released for API-key and Code Assist Enterprise users; Antigravity CLI is not an exec target here.
- The `routine` and `deny` tiers in `templates/permissions.yml`, the trust enum, the top-level `trust` and `accepted_fidelity` adapter fields and the `allowlist-fidelity` verdicts are REQ-657's; this REQ widens REQ-657's opaque `exec` sub-block into the ExecBlock, renders the tiers through the framework's renderer, and adds no entry and no second vocabulary.
- Every §6 probe is run by `adlc harness probe <name>` (REQ-664); this REQ runs no experiment of its own. For Codex, REQ-655 BR-10's `sandbox_can_reach_common_gitdir` must agree with REQ-664's `git-write-worktree` result, and disagreement refuses the adapter.
- A REQ-664 probe run and an exec run never execute concurrently on the same machine: both edit the same harness trust file, and the orchestrator refuses while REQ-664's recovery marker exists.
- id allocated with remote reservation (`degraded=0`); no degraded-allocation note required.

## Open Questions

- [ ] §6.1b is unanswered: in a linked worktree with `writable_roots` set to the repo, does `codex exec` under `workspace-write` commit, given the documented `<writable_root>/.git` read-only rule? This decides whether Codex's default strategy is `worktree`, `clone` or `orchestrator-git`. REQ-664's `git-write-worktree` probe (sub-variants `root-is-worktree` and `writable-roots-repo`) answers it and REQ-655 records the result; until that record exists the proposed default is `clone`. A `fail` verdict is a complete answer: it requires `clone` or `orchestrator-git` and leaves the adapter eligible for `verified` (BR-11); `unknown` or `n/a` is not.
- [ ] §6.3 is unanswered: without `--force`, does `agent -p` honour Cursor's `deny` rules for the deny tier, and what exit code and state does a denied command produce? REQ-664's `ask-tier-deny` entry in `cursor.json` decides it; a `fail` requires Cursor's `deny_render: none` (BR-11) and only the orchestrator gate protects the one-way moves; a `pass` on `lone-deny` without `deny-under-allow` leaves every deny-tier entry that shares a command base with a routine entry `deny_unsupported`.
- [ ] §6.6 is unanswered for every harness: what the per-command shell timeout is, whether it can be raised by config (and if so where), and whether a 120 s `adlc-read` completes. REQ-664's `shell-timeout` entry per harness decides it.
- [ ] Where each harness exposes the session id in headless output: Copilot's session-state JSONL is undocumented and may not surface in `--output-format json`; Codex's `-o` output file may carry the thread id or not. If a harness exposes none, resume is impossible on it and BR-7's halt message is the permanent behaviour there.
- [ ] `rules_reload` is unanswered for every harness: does the harness re-read a rule or config file edited mid-run, or only at startup? REQ-664's follow-up variant "rule file edited mid-run, then denied command" decides it; until it passes the value is `unknown` and is treated as `live` (BR-15).
- [ ] Gemini's documented exit codes `1`, `42` and `53`: which one a denied headless ask produces, and whether the run continues past a deny or terminates; the exit map cannot be finalised from docs, and the `ask-tier-deny` evidence in `gemini.json` is where the answer is read from.
