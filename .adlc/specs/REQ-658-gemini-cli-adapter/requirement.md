## Description

This is Phase 4 of `.adlc/research/multi-harness-plan.md` (revision 2): the
Gemini CLI adapter, built on the harness adapter framework of REQ-657 (plan
P2, the authority this REQ conforms to), on the `ADLC_HOME` / `~/.agents/skills`
groundwork of REQ-654 (P0), and on the probe results of REQ-664. It makes a
Gemini CLI install a first-class consumer of the toolkit in the same way
Copilot CLI and Cursor are after REQ-656 and Codex after REQ-655: skills
discovered from the `~/.agents/skills` mount, agents rendered into Gemini's own
format at the user level, ETHOS injected at session start, the routine-tier
allowlist and the project hooks committed in `.gemini/settings.json`, and the
deny tier — the one-way moves that on Claude Code sit behind the `ask` human
gate in session — rendered as a user-level policy deny, which is where Gemini
can express it (`deny_tier_render: {user: deny}` — project scope absent, so
unsupported there).

Gemini is the harness where the plan's §4 "what is lost" column is longest,
and the one whose future is least settled: skills activate **automatically
only**, behind a y/n consent prompt, with no `/name` or `$name` invocation;
subagents cannot nest and have **no subagent-start hook**, so ETHOS reaches a
Gemini subagent only by being prepended to its prompt; the policy `deny`
syntax that carries the deny tier is **user-level only** and cannot be
committed; the `tools.allowed` prefix allowlist is spelling-level, so every routine entry whose prefix is a prefix of, or equal to, a deny-tier spelling — bare `git`, `git -C` (both spellings being needed to cover how the pipeline actually spells its git calls, plan §2e), and the per-subcommand `git push` and `git branch` — is **omitted** from the committed render, the set computed by REQ-657 BR-8's shared-base rule rather than enumerated by hand, and those git calls prompt on Gemini; `git` and `git -C` are restorable only on the gated, probe-read conditions of BR-5 (REQ-657's rule for routine allows that wrap a deny-tier spelling), and the allowlist side is otherwise a set of declared residuals, not the gate (BR-15); an **untrusted folder** disables project
settings, hooks and commands entirely; and in June 2026 Google moved Gemini's
consumer tiers to **Antigravity CLI**, which claims to keep skills, hooks,
subagents and extensions but has not been verified to. The adapter therefore
targets the **intersection** of Gemini CLI and Antigravity CLI, and the first
deliverable is the compatibility note that establishes what that
intersection is (plan §3 P4, §6.5), citing REQ-664's `gemini.json` for every
row a probe already answers.

Seven deliverables, all additive, none of which moves or changes anything
that works today on Claude Code (plan Rule A):

1. **`harness/gemini.yml`** — the Gemini entry in the framework's adapter
   schema, in REQ-657's field names: `paths` (with each surface's `mode` and
   `write_mode`), `formats`, `tool_map`, the hook-event map (with
   `subagent-start` marked `unsupported`), `hook_payload`, `hook_timeout_unit: ms`,
   `trust: {mechanism: trusted-folders-file, detail: ~/.gemini/trustedFolders.json}`, `capabilities` (`deny: yes`,
   `subagent_start_hook: no`, `allowlist_granularity: prefix`,
   `git_c_spelling`, `fence_broad_spelling`), `deny_tier_render: {user: deny}`,
   `tier_map`, the `accepted_fidelity` map, the agent-limit keys, the
   `doctor_rows` list and the opaque `exec` block.
   Everything Gemini-specific is data in this file; the framework's renderers
   stay harness-neutral.
2. **The `.gemini/settings.json` render** written by `/init --harness gemini`:
   the canonical hook set (`ethos-inject`, `session-record`) with `timeout_s`
   converted to **milliseconds**, `tools.allowed` carrying the routine tier (the computed omitted set of git entries that prefix a deny-tier spelling, reported `inexpressible`, BR-5), and `context.fileName` listing `AGENTS.md`, merged
   under REQ-657's `write_mode: merge` (owned keys `hooks`, `tools.allowed`,
   `context.fileName`; list-valued ones replace-not-union, BR-3) into whatever the project
   already has in that file and registered as a `harness-config` drift surface
   (`/template-drift`'s, REQ-657 BR-11 — not doctor's).
3. **User-level agent renders** at `~/.gemini/agents/<name>.md` from
   `adlc agents render --harness gemini` (the agents-only subset of
   `adlc harness install --harness gemini`, REQ-657 BR-3): Gemini frontmatter
   (`name`, `description`, `tools` in Gemini's names, `model`, `max_turns`,
   `timeout_mins`), the model from REQ-657 BR-5's precedence mapped through
   the adapter's `tier_map`, the turn and time limits from tier config, and
   the ETHOS read instruction prepended to every body because the adapter
   declares `subagent_start_hook: no` (REQ-657 BR-4). Each file is a whole-file derived surface carrying the REQ-516 BR-1 header, overwritten when the render differs.
4. **User-level policy deny rules** for the deny tier (merge, deploy, force
   push, destructive cleanup — the one-way moves, plan Rule B), rendered from
   `templates/permissions.yml` by `adlc harness install --harness gemini`
   together with the agents, never committed, written as a toolkit-owned whole-file derived surface (REQ-516 BR-1 header, written only under BR-8's write rule: absent, header present, or byte-equal to a previous render, never over a headerless file; the policy file format and name are recorded in the BR-1 note); its currency is REQ-657's
   `render-currency:gemini`.
5. **`adlc doctor` Gemini rows** — `gemini:trust`, `gemini:extension` and
   `gemini:dual-install` — declared as the adapter's `doctor_rows` (kinds
   marker-present / path-exists) under the `harness:gemini` group (REQ-657
   BR-15), each with a copy-pasteable remediation. Currency of every
   user-level rendered surface (the `~/.gemini/agents/` renders and the policy
   file) is REQ-657's `render-currency:gemini`, and the committed
   `.gemini/settings.json` is `/template-drift`'s `harness-config` surface;
   neither is re-implemented here. `gemini-extension.json` itself is REQ-665's;
   this REQ only observes it.
6. **A README section** for Gemini CLI that states, in the plan's §4 terms,
   exactly what is lost on this harness and what the user must do by hand, and
   that the extension is REQ-665's pinned alternative *install route* and
   coexists with the `~/.agents/skills` mount, so Gemini lists every skill
   twice (REQ-665 BR-8) (cross-referencing REQ-665's Gemini subsection).
7. **The Antigravity compatibility note**, recorded in `.adlc/research/`
   before any adapter code is written, answering plan §6.5 and the two
   questions no probe covers, and citing `gemini.json` (REQ-664) for the
   Gemini rows of §6.4, §6.8, §6.11 and §6.12, so the adapter renders only
   what both CLIs honour.

## Business Rules

- [ ] BR-1: **The compatibility note comes first.** Before any adapter code is written, a note under `.adlc/research/` answers plan §6.5 for Gemini CLI and Antigravity CLI — from a real install of each, which of skills, hooks, subagents, extensions, policy deny, `tools.allowed` and `context.fileName` each honours, and the directory and file names each one reads — and the two questions no probe covers (OQ-3, whether a user-level policy deny outranks a project `tools.allowed` prefix allow, cross-checked against REQ-664's `deny-under-allow` and `wrapped-allow` sub-results where they have run; the row records the commands run, interactive and headless, including the chained form `echo ok && git push --force`; the extension layout is REQ-665's and is not answered here). For §6.4, §6.8, §6.11 and §6.12 it cites the probe ids (`skill-activation`, `trust-then-headless`, `session-start-context`, `fence-vs-allowlist`, `stdin-prompt`, `ask-tier-deny`, `deny-under-allow`, `wrapped-allow`; for the last two the cited status is `sub_results.<variant>.status` for gemini at the adapter's `harness_version`, never the probe's own status) and each probe's `ran_at` from `.adlc/research/harness-probes/gemini.json` (REQ-664) rather than re-recording them. The note also records the policy file format and name the adapter writes under `~/.gemini/policies/` (`paths.permissions.user`, `formats.user`), the highest rule priority the engine accepts in the user tier, the syntax of the `git -C`-wrapped deny form, and whether a hook entry accepts and preserves a `name` field (BR-3). The adapter renders a surface only when the note marks it `intersection`; a `gemini-only` surface is either rendered behind an explicit adapter flag that defaults off or not rendered, and the README names it either way. `/proceed` Phase 4 on this REQ does not start until the note exists; the architecture's task list orders the note before any `tools/adlc` task and records the note's path.
- [ ] BR-2: **`harness/gemini.yml` is data in the framework's schema, not a Gemini branch in the renderers.** Every Gemini-specific fact in the System Model (`paths` with `mode`/`write_mode`/`owned_keys`, `formats`, `tool_map`, `hook_events`, `hook_payload`, `hook_timeout_unit`, `trust` (`{mechanism: trusted-folders-file, detail: ~/.gemini/trustedFolders.json}`), `capabilities`, `deny_tier_render`, `tier_map`, `accepted_fidelity`, the per-class agent limits, `doctor_rows`, the opaque `exec` block) lives in that file. The fields REQ-657 already defines (`hook_events`, `hook_timeout_unit: ms` — the framework does the unit conversion — `capabilities.fence_broad_spelling`, `deny_tier_render` as a per-scope map, `doctor_rows`, `owned_keys`) are used as declared. Where the framework's schema lacks a field this adapter needs — per-scope `formats` for the permissions surface (`project` = `gemini-settings-json`, `user` = the policy format), a schema home for the `context.fileName` render, the limits keys of BR-7 — the field is added to the schema, bumps `schema_version` (REQ-657 Assumptions) and is documented for every adapter, so the Gemini adapter never carries a key the loader does not validate. A whole-file derived surface (the agents, the policy file) is declared as such, never as `write_mode: create` or `merge`, and `write_mode: merge` is JSON only unless the adapter's schema bump adds TOML. `.gemini/settings.json`'s `owned_keys` are `hooks`, `tools.allowed` and `context.fileName` (both list-valued, replace-not-union per BR-3, because a plain union leaves a toolkit-written entry in place forever once the render stops emitting it) (informed by LESSON-614, LESSON-716: a config the loader skips is a config nobody validates).
- [ ] BR-3: **`.gemini/settings.json` is declared `write_mode: merge` and rendered as REQ-657 BR-11 defines it, amended by the replace-not-union rule below.** The adapter's `owned_keys` are `hooks`, `tools.allowed` and `context.fileName` (the two project surfaces that live in the file, plus the instructions key): added or refreshed on each render, every other key preserved. For a list-valued owned key, merge is not a plain union. Let C be the candidate set: every string the adapter's renderer could emit for that key from `templates/permissions.yml`, `git_c_spelling`, bare `git` and `fence_broad_spelling`, regardless of the current omission decision. The merged value is `(existing − C) + current_render`, in existing order with new entries appended (an entry of the current render that is already present keeps its place). Entries outside C are the user's and are preserved. After the merge the shared-base matcher (REQ-657 BR-8) runs over the whole resulting list, user entries included; any entry that widens a deny spelling is kept but reported `user-entry-widens-deny: <entry>`, failing `/template-drift`'s `harness-config` surface and `render --check`. No marker key is written; a hand-added entry that is a member of C is therefore indistinguishable from a toolkit-written one and is replaced like it (the README residuals block says so, BR-15). The same rule applies to `hooks`: toolkit hook entries carry `name: "adlc:<id>"`, entries with that name are replaced, toolkit-named entries absent from the current render are removed, other entries are preserved. **Dependency:** REQ-657 BR-11's merge rule (list-valued owned keys unioned) needs the same amendment; this REQ is not implementable against a union rule, because a union leaves a toolkit-written widening entry in place forever once the render stops emitting it. The committed file's presence and currency in a project are `/template-drift`'s `harness-config` surface (REQ-657 BR-11), not doctor's. The renderer reads the existing file with a real JSON parser; a file that does not parse is a refusal naming the path and the parse error, and nothing is written. An existing `context.fileName` list keeps its non-candidate entries (`GEMINI.md` stays) and gains `AGENTS.md`; existing hook entries and `tools.allowed` entries that are not the toolkit's stay. The write is atomic (temp-write, rename). A second run on an unchanged project changes nothing and says so (REQ-519 BR-1 idempotency). The file is written by a serializer, never by string templating (informed by LESSON-716, REQ-519).
- [ ] BR-4: **Hooks render with millisecond timeouts under Gemini's event names.** Each entry of `templates/hooks.yml` (`ethos-inject`, `session-record`) maps its canonical events through the adapter's `hook_events`: `session-start` becomes `SessionStart`, under which both `ethos-inject` (emitting `.adlc/ETHOS.md` as added context, plan §2d) and `session-record` (whose command is REQ-660's partial, resolved through the REQ-610 BR-3 spelling and passed `--harness gemini` by the Gemini render; the entry and its render are REQ-657 BR-10's) are rendered; `session-compact` maps to Gemini's compaction event when the BR-1 note finds one (under which `ethos-inject` alone renders; `session-record` is a session-start hook), else `unsupported`; `subagent-start` is `unsupported`, renders nothing and is listed in the render's summary as "not available on gemini; ETHOS reaches subagents by prompt-prepend (BR-6, REQ-657 BR-4)". Each rendered timeout is the entry's `timeout_s` × 1000 as an integer — the framework's conversion from the adapter's `hook_timeout_unit: ms` (REQ-657 BR-10); a rendered timeout that is not an integer or differs from that product is a render error. Hook argument lookups are spelled from the adapter's `hook_payload`. The hook command is the canonical command from `templates/hooks.yml`; the renderer never takes a command from the project's own files (informed by LESSON-619, LESSON-718: a rendered config is an execution surface, and the thing being rendered into a project must not be able to choose what runs).
