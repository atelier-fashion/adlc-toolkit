## Description

This is Phase 2b of `.adlc/research/multi-harness-plan.md` (revision 2): the
first two non-Claude adapters, **GitHub Copilot CLI** and **Cursor**, built on
the harness adapter framework **REQ-657** (P2a, specified in parallel). The
framework owns the `harness/<name>.yml` schema and loader, `adlc harness
install | render | doctor --harness <name>`, the user-level agent renderer,
the allowlist renderer (routine tier plus deny tier, with the
`allowlist-fidelity` lint), the hooks renderer carrying the ETHOS
`session-start` and `subagent-start` hooks, `/init --harness` with the
`harness-config` drift surface, and `AGENTS.md` canonicalisation. This REQ
owns what is **specific to these two harnesses**: the two adapter files, the
Copilot tool-alias and model columns, the Copilot hook file and the printed
`--allow-tool`/`--deny-tool` line, the two Cursor permission files, the doctor rows, the
README's honest statement of what each harness loses, and the gate that proves
it works: `/spec` → `/proceed` on a lite REQ → `/wrapup`, end to end, on each
harness in the atelier-fashion test bed.

The plan's survey makes these two the cheapest ports because both already read
Claude Code's own files. Copilot CLI reads `.claude/settings.json` hooks,
`CLAUDE.md`, `~/.agents/skills`, and `~/.copilot/agents/*.agent.md` with tool
aliases `execute`/`read`/`edit`/`search`; it takes allowlists only as session
flags (`--allow-tool 'shell(git status:*)'`, `--deny-tool …`) or a user-level file,
never a committed one; and it needs `--trust-folder` headless. Cursor reads
`.claude/skills`, `.claude/agents`, `~/.claude/agents`, `.claude/settings*.json`
hooks and `CLAUDE.md` natively, so it needs **no agent and no hook render** at
all; its allowlist is `.cursor/cli.json` / `.cursor/permissions.json` with
`Shell(git)`-style command-base matching.

Two rules from the plan govern every rendered byte here. **Rule A**: nothing
that works today moves; every output is a new user-level file, a new committed
project file, or a printed line. **Rule B**: a harness allowlist is a
convenience for the routine tier and never the gate for the deny tier (the
one-way moves Claude renders as `ask`), so no rendered file or printed line
ever carries an auto-approve flag, and a deny-tier entry appears in a
committed file or on the printed line only as a hard deny where the harness
can express one (Cursor's `deny` at `project` scope, Copilot's `--deny-tool`
at `user` scope — the same tier REQ-662's `deny_render` re-renders at `exec`
scope), and is otherwise declared `deny-unsupported` in the adapter's
`accepted_fidelity`. A deny-tier entry whose base a routine entry shares is
never left behind a prompt the base allow has already removed: until REQ-664
proves the finer deny wins (OQ-8), both renders fail closed and omit the
routine entries sharing that base (BR-8). Residuals that no allowlist or prefix deny can close are declared, not chased (BR-17).

### Permissions

| Action | Who approves, per harness |
|--------|---------------------------|
| Run a routine-tier command (git read/write, gh read, `gh pr create`, tests, shell utilities) | the harness allowlist: Copilot session flags, Cursor permission files — except the routine entries whose base a deny-tier entry shares (`Shell(git)`, `Shell(gh)` on Cursor; `git push:*`, `git branch:*` and the `git -C` prefix on Copilot), which BR-8 omits while OQ-8 and OQ-9 are open, so they prompt at the harness (on Copilot that includes every `git -C …` call) and the operator is told so |
| Run a deny-tier command (`gh pr merge`, deploy, `terraform`, `git push --force`, `rm -rf`) | a human, always: on Copilot the printed line's `--deny-tool` (a hard deny at `user` scope, re-rendered at `exec` scope by REQ-662), so the operator runs it from their own shell; on Cursor a hard `deny` where the base is not shared, so the operator runs it from their own shell (BR-8, BR-13); a shared-base entry is `deny-unsupported` and stays behind the harness's own prompt because the base allow is omitted (BR-8 fail-closed, Rule B) |
| Write a user-level render (`~/.copilot/agents`) | the operator running `adlc agents render --harness copilot` / `adlc harness install --harness copilot` |
| Commit a project render (`.github/hooks/adlc.json`, `.cursor/*.json`) | the operator; a lite-lane PR cannot touch them (BR-12) |

## Business Rules

- [ ] BR-1: `harness/copilot.yml` and `harness/cursor.yml` exist, load through the REQ-657 loader without warnings, and declare every field the REQ-657 schema requires with the facts in the Entities table (the spellings there are illustrative; the schema's are binding). The adapter files carry no literal `~/.claude`, `~/.copilot` or `~/.cursor` path (plan §5 `no-harness-path`); paths derive from `ADLC_HOME` and `HOME` per REQ-654 BR-1. A field this REQ cannot verify on a real install (a model id, the exec flags for P6) is written as `unverified`, never guessed (informed by REQ-654, LESSON-716).
- [ ] BR-2: **Rule B is structural.** No rendered file and no printed line produced for either harness contains an auto-approve flag or setting (`--allow-all-tools`, `--force`, `--yolo`, a wildcard allow, or an equivalent). Deny-tier entries of `templates/permissions.yml` (the one-way moves Claude renders as `ask`) appear only under a Cursor `deny` or a Copilot `--deny-tool`, and only where that harness's granularity can express the deny without blocking a routine entry; every other deny-tier entry is declared `deny-unsupported` in that adapter's `accepted_fidelity` and named in the fidelity report (BR-6, BR-8) — never under an allow, never dropped silently. A test asserts this over every render fixture for both harnesses and over the printed line, and finds no deny-tier command, in plain or wrapped (`git -C <path>`) form, that any rendered allow rule matches **under that harness's own matching semantics** (command-base for Cursor, subcommand prefix for Copilot), asserted by a matcher per granularity, not by name. No rendered allow, for either harness, has a first token in {`if`, `sh`, `bash`, `zsh`, `env`, `xargs`, `eval`, `exec`, `sudo`, `time`, `command`, `nohup`, `python*`, `node`}; a routine entry whose first token is in that set is omitted, reported `inexpressible` and declared in `accepted_fidelity`. Any broad fence spelling is a separate printed remedy labelled "WIDENING, not applied", never part of the paste-ready line (informed by LESSON-663, LESSON-619).
- [ ] BR-3: `adlc agents render --harness copilot` writes one `<name>.agent.md` per canonical `agents/<name>.md` into the **user-level** `~/.copilot/agents/`, never into `.github/agents/`; a `--project-agents` opt-in is out of scope here and in REQ-657 (plan M7). The tool map is exact: `Read` → `read`; `Grep`, `Glob` → `search` (one `search` entry, deduplicated); `Edit`, `Write`, `NotebookEdit` → `edit`; `Bash` → `execute`; `Agent` → `unsupported` (dropped from the list, no restraint line, REQ-657 BR-4). A canonical file with no `tools:` line yields no `tools:` line (all tools; `task-implementer` and `pipeline-runner`). A canonical tool name the map does not know never reaches the render: REQ-657 BR-1's loader rejects a `tool_map` that omits a tool any `agents/*.md` uses, naming the field, so this REQ adds no render-time check of its own and no silent drop is possible — a dropped restriction would turn an enforced read-only reviewer into an unrestricted one (informed by LESSON-716, LESSON-614). The render is idempotent and the result is covered by the framework's `render-parity --check`.
- [ ] BR-4: The Copilot `model:` line is REQ-657 BR-5 applied to this adapter's `tier_map`: the tier config resolves each agent to an alias, the alias is mapped through `harness/copilot.yml` `tier_map`, and a value of `unverified` (or a missing entry) **omits** `model:` so Copilot applies its own default, saying so once on stderr per render. No new mechanism is added. A guessed model id that the harness rejects would make every rendered agent unusable; omitting is the fail-safe. The same rule binds the Cursor `tier_map` should Cursor ever need a render. Which ids fill the map is Open Question 4.
- [ ] BR-5: `/init --harness copilot` and `adlc harness render --harness copilot` write `.github/hooks/adlc.json` from `templates/hooks.yml` through the Copilot adapter's event map: `sessionStart` carries both canonical session-start hooks — `ethos-inject` (emits `.adlc/ETHOS.md` as additional context when the file exists, nothing otherwise) and `session-record` (whose command is the partial REQ-660 BR-8 ships, resolved through the REQ-610 BR-3 spelling) — and `subagentStart` carries `ethos-inject`; each entry's `timeout_s` is mapped onto Copilot's per-hook timeout field. Both this file and the framework's `.claude/settings.json` render come from one source (`templates/hooks.yml`), rendered through the Copilot adapter's `hook_events` and `hook_payload`, so the two renders share the entry, not the byte string: the Copilot render passes `--harness copilot` to the session-record partial, while the shared `claude` hooks render passes no harness argument and REQ-660's partial detects the harness from the payload through its embedded table (Cursor's row lives only in that partial). The file is project-relative, carries no secret and no absolute user path, and is registered on the `harness-config` drift surface (REQ-525 BR-4 cross-reference invariant). Copilot's documented hook contract takes context only as a JSON object on stdout with an `additionalContext` string, and plain text on stdout is not injected, so the Copilot render passes the ethos partial the output key through the adapter's `hook_output` map and the partial wraps the file in that object; the shared `claude` render stays plain stdout. ETHOS reaches a Copilot session **exactly once**; Open Question 1 settles how, and the dogfood run verifies it (informed by REQ-525, LESSON-019, LESSON-755).
- [ ] BR-6: Because Copilot has no committed allowlist, `/init --harness copilot` and `adlc harness render --harness copilot` **print** one line the user pastes into a shell alias or profile: a `--allow-tool` entry for every routine-tier entry of `templates/permissions.yml` in Copilot's `shell(<prefix>)` syntax, in the plain spelling (the `git -C` spelling from the adapter's `git_c_spelling` is omitted, see below). `fence.partial-source` is not on the line: a `printed` render obeys REQ-657 BR-8's committed-scope fence rule, so it is omitted, reported `inexpressible`, declared in `accepted_fidelity`, and the fence prompts (plan §2e limits 1 and 2). A broad fence spelling, if the operator wants one, is a separate printed remedy labelled "WIDENING, not applied", never part of the paste-ready line. The same line carries one `--deny-tool` entry per argv prefix of each deny-tier entry's `commands` (or that prefix declared `deny-unsupported`) in Copilot's deny syntax: Copilot declares `deny_tier_render: {user: deny}` — it has no committed project surface, so the printed line **is** the user-scope render and the deny tier is a hard deny there; REQ-662's `deny_render: flags` re-renders the same tier at `exec` scope, keyed on `capabilities.deny: yes`, so the two cannot disagree on which commands are denied. BR-8's shared-base fail-closed rule applies to the printed line too: a routine prefix that is a proper prefix of, or can wrap, a deny-tier spelling under Copilot's own matching semantics — `git push:*` covers `git push --force`, `git branch:*` covers `git branch -D`; the wrappers are `git -C <path>`, env-assignment prefixes and `bash -lc` — is omitted from the `--allow-tool` entries and reported `inexpressible`, the `--deny-tool` for the deny-tier entry is still printed, and the operator is told which prefixes will prompt, until `capabilities.deny_under_allow` reads `pass` for the `prefix` shape (REQ-664 `deny-under-allow`, OQ-8) and, for the bare `git -C` prefix, also the `git-c` shape (REQ-664 `wrapped-allow`, OQ-9), at the adapter's `harness_version`. The `env-prefix` and `shell-opener` shapes stay `unverified`, so no REQ-664 result lifts an omission resting on them and those wrapped spellings are declared residuals (BR-17). First-token fence entries are never rendered. Alongside the line the `allowlist-fidelity` report states what subcommand granularity loses, and every such loss — the omitted fence entry as `inexpressible`, the omitted `git push:*`/`git branch:*` prefixes and the `git -C` prefix as `inexpressible`, any deny-tier spelling Copilot's syntax cannot carry as `deny-unsupported` — is declared in `harness/copilot.yml` `accepted_fidelity` (REQ-657 BR-9), so `allowlist-fidelity` passes with the loss visible rather than failing. The `git -C` allow spelling from `git_c_spelling` is a bare prefix (`shell(git -C:*)`) and therefore covers every git subcommand, including `git -C <path> push --force`, `reset --hard`, `clean -f` and `branch -D`, none of which a `--deny-tool` on the plain spelling matches. It is a routine prefix that covers a deny-tier spelling and is omitted under the same fail-closed rule, reported `inexpressible` for every `git.*` routine entry it would have doubled, and declared in `accepted_fidelity`. The omission is lifted only by `deny_under_allow.git-c` reading `pass`, from a REQ-664 `wrapped-allow` result showing that a `--deny-tool` on the plain spelling denies a `-C`-spelled command, read only when REQ-664's `allow-only-git-c` control shows the `-C`-spelled push landed (OQ-9). The fidelity report tells the operator that `git -C …` calls will prompt. - The harness facts in the Entities table are the plan's docs-verified survey as of 2026-10-27 (plan §1, §4, §7). Where the dogfood run contradicts one, the adapter file and the README change together, and the plan's §8 changelog gets a row.
- `templates/permissions.yml` (REQ-657) names the routine and deny tiers semantically (`git.read`, `gh.pr.create`, `gh.merge`, `fence.partial-source`, …); this REQ renders those ids, it does not define them.
- Copilot's `subagentStart` hook is rendered as BR-5 states, but neither adapter declares `subagent_start_hook: yes` before a real run shows the hook reaching a subagent: a `no` keeps REQ-657 BR-4's ETHOS-first line in every rendered Copilot agent, so a hook that does not fire costs nothing and one that does fire costs one repeated read. - Cursor reads both `~/.agents/skills` (the skills-only view) and `~/.claude/skills` (the clone root), so every toolkit skill is discovered twice and the clone root's non-skill directories are exposed through the second path; the doctor row and the README state it (BR-10, BR-11), and whether the duplication confuses Cursor's skill picker is answered by the dogfood run, not by experiment here.
- The dogfood runs are interactive: Copilot's trust prompt and Cursor's are answered by the operator; `--trust-folder` and `--trust` are recorded in the adapters for P6 and not exercised here.
- id allocated with remote reservation (`degraded=0`); no degraded-allocation note required.
