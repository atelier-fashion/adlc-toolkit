## Description

`.adlc/research/multi-harness-plan.md` §6 lists twelve things that must be
verified on a real install before the harness adapter specs are written, and
§3 gates the phases on them: P1 on §6.10, P3 on §6.1a, P4 on §6.4 and §6.5,
P6 on §6.1b, §6.3, §6.8, §6.11 and §6.12. Today each item is a sentence in a
research note. Answering one means a person hand-builds a repo, hand-edits a
harness config, runs a headless command, reads the output, and remembers to
undo the config edit. The answer lives in that person's head or in a chat
transcript, it is tied to whichever harness version happened to be installed,
and it cannot be re-asked after an upgrade without doing it all again. The
adversary pass on the plan (§8) turned several "documented" claims into open
questions precisely because nobody had run them.

This REQ makes the twelve items **scripted, repeatable probes** behind one
command whose only writes outside its throwaway directory are a reverted
trust entry in a harness user config and, on `gemini`, one probe-named policy
file that is deleted again (BR-4), the recovery marker under
`$ADLC_HOME` that covers those files from before the first edit until its
checksum-verified restore (BR-4), and the result file and fixture in the
caller's repo (BR-9, BR-10):

```
adlc harness probe --list
adlc harness probe <claude|copilot|codex|gemini|cursor> [--only <probe>]... [--dry-run] [--keep] [--timeout <s>]
adlc harness probe <claude|copilot|codex|gemini|cursor> --recover
```

Against the harness binary that is already installed on the machine, it
builds a throwaway git repository (with a local bare `origin` and a linked
worktree), writes the project-local hook, allowlist, skill and trust fixtures
each probe needs, launches the harness headlessly with a short single-purpose
prompt, and decides every verdict from a **side effect it checks itself** (a
ref advancing in the bare remote, a sentinel file, a nonce in captured
output), never from what the model says it did. It then removes the repository
and restores every user-level file it touched byte for byte. The outcome is
one JSON file per harness under `.adlc/research/harness-probes/` naming the
harness version, the date, and `pass` / `fail` / `unknown` / `n/a` per probe with
the evidence captured, so the gated REQs can cite a result rather than a belief,
and `adlc harness detect` (REQ-654) shows when each harness was last probed.

The probes run **before** the adapter REQs exist, because their purpose is to
gate them. So the command carries its own minimal per-harness launch profile
as data, needs nothing from `harness/<name>.yml`, nothing from the renderers,
and nothing mounted into any harness; everything it needs inside the
throwaway repo it writes itself. The probes cover exactly what the plan asks
and nothing the plan does not: a bad result is a finding for the plan, not a
bug in the probe. (informed by LESSON-012, LESSON-395)

## Business Rules

- [ ] BR-1: `adlc harness probe` is a new pure-stdlib `adlc` subcommand under the `harness` group REQ-654 introduces (REQ-519 BR-11 data-driven dispatch; LESSON-395: it must run on a machine where nothing it diagnoses is set up — no venv, no delegation, no toolkit mounted in any harness). `<name>` must be one of the five profiles and is required for every form except `--list`; an unknown name is a usage error. When the profile's binary is absent from PATH and the form would launch it, the command exits 2 with a message naming the binary and **writes no result file**: a result file means the harness was exercised. `--list` prints the catalogue (id, plan item, applicability, oracle) and `--dry-run` additionally prints the launch count and the user-level files the run would edit, both without launching anything and both usable outside a git repo (BR-9); `--recover` is BR-4's recovery form: it launches nothing and needs neither a git repo nor the harness binary on PATH (it reads only the marker and the files the marker names). (informed by REQ-519, LESSON-395)
- [ ] BR-2: The probes depend on no adapter. The per-harness knowledge they need (HarnessProfile) is one data table inside the probe module; the module imports nothing from `harness/`, from `tools/adlc/harness/*.py` renderers, from the current repo's `.adlc/`, or from any skill, and it reads neither `templates/permissions.yml` nor `partials/README.md` at run time: the routine set and the canonical fence it needs are data carried in the module (BR-7). It never requires `~/.agents/skills`, `~/.claude/skills` or any agents directory to exist or to point anywhere, and it never reads or writes a harness's user-level skills, agents or hooks directories. Its only user-level writes are the files BR-4 enumerates (the trust entry and, on `gemini`, the probe-named policy file), each under BR-4's contract. When P2 lands its `harness/<name>.yml`, replacing the table with the adapter is P2's change, not a constraint on this one.
- [ ] BR-3: Every run works in a fresh ProbeRun directory from a validated `mkdtemp` (the result is checked to be a non-empty absolute path under the temp root before any `rm -rf` is derived from it — LESSON-619, LESSON-441) holding its own repo, bare `origin`, linked worktree and captured output. The harness is launched with cwd inside that repo or worktree, never in the caller's repo and never in `$HOME`. Git identity is set in the throwaway repo's own config, so no global identity is required and none is written. The directory is removed at the end of the run, on success and on failure alike; `--keep` retains it and prints its path. A removal that fails is reported with the exact path in `cleanup.leftovers` and makes the exit code 1 (BR-11). (informed by LESSON-619)
- [ ] BR-4: User-level files are edited only for a `user-config-entry` or `trusted-folders-file` trust mechanism and, on `gemini` alone, for the one probe-named policy file `ask-tier-deny` needs (Gemini has no project-local deny location). The trust entry covers both the run's `repo` and its `wt`, each keyed by its `realpath`; on `gemini`, `ask-tier-deny` also writes one probe-named policy file in Gemini's user-level policy location (`~/.gemini/policies/`), under the same backup, marker and checksum-verified restore (the backup records `absent` and the restore deletes the file), written at run start together with the trust entry; its rules name only the variant-specific deny sentinels and refs of BR-16 (one distinct path per variant), never a control's. Every such file is under one backup-restore contract: checksum and copy the file into the run's backup directory **before** the edit (a file that does not exist yet — an absent user config, the policy file — is recorded `absent` and deleted on restore), write the edit atomically, restore the backup on every exit path including a catchable signal, and verify by checksum that the restored file is byte-identical (or absent). If at restore a user file's checksum is not the post-edit checksum the probe recorded (something else changed it during the run), the restore does not overwrite it: it removes only the added entry, reports `user_files_restored: surgical` (exit 1, BR-11), and keeps a backup copy beside the marker under `$ADLC_HOME`, printing its path. For the wholly probe-owned policy file there is no entry to remove surgically: surgical restore there means copying the file beside the marker under `$ADLC_HOME`, deleting it, and reporting `surgical`. A covered file whose current checksum equals its backup checksum (a crash before the edit landed) needs nothing and is a no-op restore. The entry (and the policy file) is written once at run start, before the first launch, and revoked by the restore at run end; `trust-then-headless` is therefore the run's first launch, and its `allowlist-loaded` sub-result — not the probe's own status, which also folds in `hooks-loaded` — is the precondition every trust-dependent probe records. "Trust-dependent" means every other launched probe on a `user-config-entry` or `trusted-folders-file` harness (`codex`, `gemini`); when `allowlist-loaded` is not `pass` they record `unknown` / `precondition-unmet: trust-then-headless <allowlist-loaded status>`. On such a harness `--only <x>` for any other probe launches `trust-then-headless` implicitly, counts it in the launch count (BR-12) and writes its entry. The trust entry names only the run's two throwaway paths, so nothing the user owns is widened. The recovery marker is written under `$ADLC_HOME` **before** the first edit and cleared only **after** the checksum-verified restore (or the verified surgical removal), so a run that dies between the two leaves it in place as the crash signal, naming each backup and its checksum and, in `created_dirs`, each directory that was absent when the marker was written, deepest first (for example `~/.gemini/policies` before `~/.gemini`); the marker is rewritten atomically after each edit with that file's post-edit checksum, and restore and `--recover` remove a `created_dirs` entry with `rmdir` — never recursively — only if it is empty (a non-empty one is left and listed in `cleanup.leftovers`); the next run on that harness refuses to start until `--recover` has restored it, `--recover` restores, verifies and clears the marker and needs neither a git repo nor the harness binary, and a concurrent REQ-662 exec run is refused by REQ-662 while this marker exists. Harnesses whose trust is a launch flag get the flag and no file edit; `claude` gets neither. (informed by REQ-519 BR-2, LESSON-017 via REQ-522 BR-8)
- [ ] BR-5: A verdict is decided only by a side effect the probe observes itself — a ref in the bare remote, a sentinel file, a nonce in captured stdout, a located file — never by the model's prose claim; harness stdout is data to search, not a report to believe (LESSON-008). **Nonce transform:** a nonce is never asked for verbatim, because the prompt contains it and an echo of the prompt would satisfy the oracle; the ask requests it transformed ("reply with the nonce reversed"), the nonce is 8 lowercase alphanumeric characters, random, drawn fresh for each launch (BR-16) and never a palindrome, the oracle matches the reversed string, and only the final assistant message is searched — as the profile's `final_message` extractor returns it (`json` `.result`, a last-message file, and so on), never tool-call records, prompt echoes or the rest of the stream; a profile with no such extractor, or an output from which no final message can be delimited, records `unknown` / `precondition-unmet: no delimited final message` for every nonce oracle. The oracle searches the **full capture**, never the capped evidence tail of BR-9: the cap bounds what is written to the result file, not what is decided on. The vocabulary is closed: `pass` = the harness exited 0 and the oracle is positive; `fail` = the harness exited 0 and the oracle is negative; `unknown` = anything else (non-zero exit, timeout, a launch the harness refused, a precondition the probe could not establish), always with a `reason`; `n/a` = the probe does not apply to this harness, with the reason. A catalogue row may declare that a non-zero **session** exit does not force `unknown` (`ask-tier-deny`: a held deny may legitimately end the session non-zero; `shell-timeout` likewise). The exception covers the exit code only: `timeout`, `launch-refused` and `precondition-unmet` still record `unknown` on these rows. Because a session that never reached the ask also leaves the sentinel absent, both rows pair the ask with a nonce reply — "…, then reply with the nonce reversed and nothing else" — and decide: sentinel present → `fail` (`ask-tier-deny`) / `pass` (`shell-timeout`); sentinel absent and the reversed nonce in the final assistant message → `pass` / `fail`; sentinel absent and no reversed nonce → `unknown` / `ask-not-reached`. A harness that aborts the session on a deny (gemini exit 42/53) never emits the nonce reply, so `pass` is unreachable on it and `ask-tier-deny` records `unknown` / `ask-not-reached` with the exit code in evidence. Because a headless ask is already a deny, `ask-tier-deny` also runs four controls (`baseline`, `allow-only`, `baseline-git-c`, `allow-only-git-c`), recorded in `sub_results` and excluded from the disjunction, and gates each variant on them and on a config witness as BR-17 states (`lone-deny` is `n/a` / `not-applicable: headless ask is already a deny, an absent sentinel proves nothing` unless `baseline` left its sentinel present). The exit code is recorded in evidence either way. For probes with variants, the probe's status is derived from the variant statuses as the `sub_results` row states (conjunction for `trust-then-headless`, whose all-`n/a` and `unknown`-half cases that row states; disjunction for the rest, `ask-tier-deny` included); a probe with no applicable variant is `n/a` with the first reason. A model that exits 0 having refused the ask therefore records `fail` with its output in the evidence, which is the honest result: the oracle cannot tell a harness that blocked the action from a model that declined it, and the evidence is what lets a reader tell. (informed by LESSON-008, LESSON-012)
- [ ] BR-6: The catalogue in the System Model is the complete probe set and the complete §6 mapping. Every one of the twelve items appears in the result's `coverage`: as `{probes: [...]}` naming the ids that answer it (with a `note` where only part of the item is answered — `6.1a`'s `"headless only"`), or as `{status: "not-probed", reason}` with the reason given in the catalogue. Adding a probe is one catalogue row, one table entry and one oracle function; nothing in dispatch, output or `--only` changes. `--only <probe>` accepts a catalogue id, may be repeated, and rejects an unknown id before anything is launched. `coverage["6.3"]` lists `ask-tier-deny` and `git-write-main` (the deny half and the routine-allow half of §6.3). REQ-662 BR-11's required set is cited by id (`git-write-worktree`, `git-write-main`, `trust-then-headless`, `session-start-context`, `stdin-prompt`, `fence-vs-allowlist`, `shell-timeout`, `ask-tier-deny`); `unknown` and `n/a` both read as REQ-662's `unverified`. The evidence path REQ-662 cites is this REQ's result file, not a `.adlc/research/probes/<harness>/` directory. REQ-658's Antigravity note and REQ-666's §6.10 record cite `gemini.json` and `claude.json` respectively rather than re-running probes.
- [ ] BR-7: Each probe writes exactly the set-up its catalogue row names, in the harness's own project-local spelling as plan §1 records it, and asks exactly its one-line ask. The allow rules written are the per-probe nonce commands plus, where the probe is about them, the routine set (the four classes named explicitly in the module (git read, git write, gh read, shell utilities, each an explicit entry list), pinned by the AC-7 test as a subset of the routine allow entries of whichever source exists: `templates/claude-settings-template.json` until REQ-657 merges, `templates/permissions.yml` after; REQ-657 re-points this test in the change that deletes the template) rendered into the harness's spelling; the deny tier is never allowed (plan Rule B — `ask-tier-deny`'s `deny-under-allow` and `wrapped-allow` allow one command *base*, or `git -C` while the deny names the plain spelling, under a finer deny, which is the Rule B question itself, not a grant of the deny tier; the `allow-only*` controls run the denied command with no deny installed, writing a ref only to the throwaway bare remote). The probe never passes `--yolo`, `--force`, `--allow-all`, `--dangerously-skip-permissions`, `danger-full-access` or any equivalent as a launch flag or setting: `ask-tier-deny` exists to measure their absence, and a probe that granted them would measure nothing (the `wrapped-allow` ask text names `--force` as the command the deny must stop; that text is a prompt body, not part of the captured command line). The fence in `fence-vs-allowlist` is the REQ-610 BR-3 canonical spelling and the routine set is the explicit four-class list above: both are data carried in the probe module, the fence copied from `partials/README.md`'s documented form rather than retyped, the routine set written as explicit entry lists, both pinned by the AC-7 test and never read from either source at run time — so the probe tests what the skills actually emit while still running on a machine with no toolkit mounted (BR-2). (informed by REQ-610, LESSON-663)
- [ ] BR-8: Every launch runs under a wall-clock cap (default 300 s, `--timeout <s>` overrides; when `shell-timeout` is among the probes selected to run, the cap floor is 180 s — the 125 s sleep plus the model's turnaround — and the command refuses a smaller cap with exit 2 before launching anything), such that no child outlives an expired launch and the harness can never block on output, with stdin closed after the prompt is delivered. A killed launch records `unknown` / `timeout`. The harness inherits the caller's environment (it needs its own credentials) minus nothing; the probe adds no `ADLC_*` or credential variables of its own.
- [ ] BR-9: The result file is written atomically to `<repo root>/.adlc/research/harness-probes/<harness>.json`, the repo root resolved from the caller's cwd via `git rev-parse` (LESSON-397); outside a git repo the command refuses before launching anything, except for `--list` and `--dry-run`, which write nothing and work anywhere, and `--recover`, which writes no result file and needs no repo. It carries every ResultFile field. With `--only`, entries for probes not run are **carried forward** from the existing file only when its `harness_version` and `probe_tool_version` both match the current run; otherwise they are replaced by `unknown` / `not-run-this-version`, so a result never silently mixes harness versions. The file-level `ran_at` and `date` are the latest run's; each probe keeps its own `ran_at`. Every captured string is passed through a stdlib credential-redaction pass equivalent to `partials/intake.sh`'s chain (architecture decides whether it is ported or shared) and has `$HOME` rewritten to `~` before it is written, because the file is meant to be committed. Stdout and stderr tails are capped per probe (a per-probe evidence cap, OQ-3) so a result file stays reviewable. (informed by LESSON-007 via REQ-515, LESSON-397)
- [ ] BR-10: `transcript-locate` copies at most the first N records of the located session file, redacted the same way, to the TranscriptFixture path, and records in its evidence the `~`-relative location and the discovery rule that found it (directory encoding, `cwd` field, mtime, or `hook-reported` on `cursor`). It never modifies or removes the harness's own session records: those are the harness's state, not the probe's, and leaving them is stated in Assumptions.
- [ ] BR-11: Exit codes: 0 when every applicable probe ran to a verdict (verdicts are data — a run full of `fail` still exits 0); 1 when the probe tool itself failed or refused to proceed (a cleanup that left something behind, a restore whose checksum did not match (including a `surgical` one), a result file that could not be written, a refusal because a recovery marker exists, a refusal because a launching form's cwd is outside a git repo), with every leftover path and the `--recover` command printed; 2 for usage errors and an absent binary. A cleanup or restore failure is never downgraded to a warning (LESSON-572: the audience of the message is a human who must act, so it is loud and names the exact paths). (informed by LESSON-572, BUG-195)
- [ ] BR-12: Before the first launch the command prints the launch count and the harness it will spend them on, because every launch is a model session on the user's own account, and the count includes the controls (`ask-tier-deny` alone is seven launches: three variants and four controls); `--dry-run` is the way to see the plan without paying. No confirmation prompt is added: invoking the command is the consent, and a prompt would break the unattended re-run the gated REQs want.
- [ ] BR-13: `adlc harness detect` (REQ-654 BR-7) gains a `last_probe` column per harness: the `date` of the current repo's result file for that harness, `never` when there is none, `unreadable` when the file does not parse; `--json` gains `last_probe` and `probe_file`. It stays read-only and never fails on the new column; outside a git repo the column is `never`. (informed by REQ-654)
- [ ] BR-14: The probe tool is tested without any real harness: `tools/adlc/tests` gains a **fake harness binary** (a shell script on a sandbox PATH, driven by a scenario variable) that mimics each profile's headless CLI well enough to either perform or refuse each probe's side effect, hang, or exit non-zero, so every verdict path of every probe, the `--only` merge rules, the redaction, the `~` rewrite, the result schema, and the `detect` column are exercised under pytest. Cleanup is proven by a before/after listing of the sandbox `HOME` and temp root, trust-file restore by checksum, and crash recovery by killing the fake run between edit and restore and asserting that the next run refuses until `--recover`. The fake harness and any shell the probe writes into fixtures are POSIX-sh and bash 3.2 safe (no `case` inside `$( )`, no `local`, no `[[`). (informed by LESSON-395, LESSON-582, LESSON-012)
- [ ] BR-15: Documentation lands in the same change: `tools/adlc/README.md` (the subcommand, the catalogue, the exit codes, the recovery procedure), `CHANGELOG.md`, and one line per §6 item in `.adlc/research/multi-harness-plan.md` naming its probe id or its `not-probed` reason, so the plan and the tool cannot drift apart silently. The README also states BR-18's residual beside every statement that a `pass` lifts an omission. (informed by LESSON-019)
- [ ] BR-16: Every launch — variants and controls alike — starts from fresh state that no earlier launch can have influenced. Before each launch the probe deletes all sentinels, resets the bare remote's probe refs to their set-up state and draws a fresh nonce (BR-5); each launch's sentinel and ref names are unique to that launch (the launch id is part of the name); and the oracle asserts every sentinel and ref its verdict reads is **absent** before the launch, recording `unknown` / `precondition-unmet: stale state before launch` otherwise. **Gemini variant isolation:** the `gemini` policy file is user-level and live for the whole run (BR-4), so its rules name only variant-specific sentinels and refs, a distinct path per variant, and each control uses its own control sentinel and ref which no policy rule names; a variant's deny is therefore never in force during a control or another variant. The only difference between a control's command and its variant's is that launch-unique path token.
- [ ] BR-17: `ask-tier-deny` proves nothing unless the allow it sits under was necessary and effective and the config was loaded. (a) `deny-under-allow` is decided by the three-way rule (BR-5) only when `allow-only` left its sentinel present **and** `baseline` left it absent; `wrapped-allow` only when `allow-only-git-c` left the ref present **and** `baseline-git-c` left it absent. An `allow-only*` control that left its effect absent gives `unknown` / `precondition-unmet: allow-only control did not run the command` (`allow-only-git-c control did not run the command` for `wrapped-allow`); a `baseline*` control that left it present gives `unknown` / `precondition-unmet: allow not required (baseline ran the command)` (`baseline-git-c ran the command` for `wrapped-allow`). (b) `lone-deny` stays `n/a` wherever the headless ask is already a deny (`baseline` left no sentinel). (c) The profile may declare `allow_required_path`, a path outside the sandbox's writable roots, so the allowed command cannot succeed without the allow; it is declared explicitly for `codex`, whose `workspace-write` also treats the temp root as writable; where none is declared, necessity rests on the `baseline` controls alone. (d) **Config witness:** each variant's config also carries an allow for the distinct command `touch <witness-sentinel>`; the ask runs the witness first, then the denied command, then the nonce reply; `pass` additionally requires the witness present, and a witness absent gives `unknown` / `precondition-unmet: config witness absent`, because a config that did not load cannot show a held deny. The controls carry no witness: they are decided by their own command's effect alone. (informed by LESSON-012)
- [ ] BR-18: Consumer mapping and residual. `ask-tier-deny` answers two wrapper shapes: `git-c` from `wrapped-allow` and `prefix` from `deny-under-allow`. The `env-prefix` and `shell-opener` wrapper shapes have no sub-variant in this REQ and therefore stay `unverified` forever here; REQ-657's `capabilities.deny_under_allow` for those shapes can only be `unverified`, and no result file of this REQ lifts it. Residual: a launch is a single model sample, so model non-determinism can still give a one-off hollow `pass` (for example a model that declines the command for its own reasons after running the witness); the byte-identical controls (BR-16) and the witness (BR-17) bound it and do not remove it, and any `pass` that lifts an omission carries that residual in the README (BR-15).
