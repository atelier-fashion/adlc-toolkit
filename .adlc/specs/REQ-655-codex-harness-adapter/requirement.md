## Description

This is Phase 3 of `.adlc/research/multi-harness-plan.md` (revision 2): the
Codex CLI adapter, built on the harness adapter framework REQ-657 specifies
(the `harness/<name>.yml` schema and loader, `adlc harness
install | render | doctor --harness <name>`, the user-level agent renderer, the
allowlist renderer with `allowlist-fidelity`, the hooks renderer,
`/init --harness` and the `harness-config` drift surface). REQ-654 (P0)
already gives the toolkit a variable home, the `~/.agents/skills` mount that
Codex reads, `adlc harness detect` and a report-only `harness:codex` doctor
check. This REQ adds nothing to those; it fills in the Codex column of the
framework so that a Codex user gets the same skills, agents, ETHOS injection,
routine-tier autonomy and delegation routing a Claude Code user has, rendered
into the formats Codex reads. REQ-657's "Vocabulary this REQ fixes for its
siblings" is the authority for every spelling below; where this spec and
REQ-657 differ, REQ-657 wins.

What Codex reads, and therefore what this REQ renders (all from
`.adlc/research/codex-portability.md` §1–§2 and the plan §1):

- **Skills** from `~/.agents/skills` (already mounted by REQ-654; nothing here).
- **Agents** as TOML roles in `~/.codex/agents/`, with `name`, `description`,
  `developer_instructions`, optional `model` and `model_reasoning_effort`, and
  **no tool restriction**: a Codex subagent inherits the parent's sandbox and
  skills. Seventeen of the toolkit's nineteen agents have a `tools:` line that
  omits Edit and Write (thirteen `Read, Grep, Glob, Bash`, three
  `Read, Grep, Glob`, one `Bash`); the two orchestrator/implementer agents have
  no `tools:` line. On Codex that restraint cannot be enforced, so the adapter
  declares `capabilities.agent_tool_restriction: none` and the framework
  renderer (REQ-657 BR-4) writes one restraint sentence as the **first
  instruction line** of `developer_instructions` for each of the seventeen;
  the sentence is the framework's, not Codex-specific, and the README says it
  is honour-system.
- **Hooks** in `.codex/hooks.json`, using Claude's event names (`SessionStart`,
  `SubagentStart`, …), mapped through the adapter's `hook_events`. The ETHOS
  hook fires on both, so a Codex subagent reads
  `.adlc/ETHOS.md` the same way a session does (plan §2d). Because the adapter
  declares `subagent_start_hook: yes`, no ETHOS prepend line is rendered into
  the agents (REQ-657 BR-4).
- **A committable command allowlist** as Starlark `prefix_rule(pattern=[…],
  decision="allow"|"prompt"|"forbidden")` in `.codex/rules/*.rules`. The
  routine tier of `templates/permissions.yml` renders as `allow`, minus the routine entries `["git", "push"]`, `["git", "branch"]` and `["git", "-C"]`, which are omitted unconditionally and reported `inexpressible` (BR-3); the deny
  tier (`templates/permissions.yml`) renders as `prompt` in the committed
  project render, because the adapter declares `deny_tier_render: {project:
  confirm}` (REQ-657 BR-6: a human confirms in session; plan Rule B: a harness
  allowlist is a convenience for the routine tier, never a grant for the deny
  tier; the `user` scope is absent, i.e. `unsupported`). `forbidden` appears
  only in the exec-engine render REQ-662 owns (`exec.deny_render: file`, keyed
  on `capabilities.deny: yes`).
- **`.codex/config.toml`** with `sandbox_mode = "workspace-write"` and
  `approval_policy = "on-request"`, the only sandbox posture this REQ ships.
- **`AGENTS.md`** read natively as the project instruction file (REQ-657's
  canonicalisation; this REQ makes `/init --harness codex` guarantee it exists).
- **`~/.codex/AGENTS.md`** as the global instruction file, which is where the
  delegation installer's routing block goes (today it goes only to
  `~/.claude/CLAUDE.md`).
- **Project layers load only for trusted paths** (`projects.<path>.trust_level`
  in the user config; REQ-657 trust enum `user-config-entry`), so the README
  and `/init` say what the operator must trust before `.codex/` is honoured.

**The gate.** Codex documents `<writable_root>/.git` as read-only under
`workspace-write`. If an `allow` rule for `git commit` does not run it
unprompted under `approval_policy = "on-request"`, every commit, worktree add
and push in `/proceed` becomes an approval event and the adapter delivers
correctness but not autonomy. The plan (§6.1a, §6.1b) requires this to be
verified on a real Codex install in a main checkout **and** in a linked
worktree (whose git data lives in `<repo>/.git`, outside a sandbox rooted at
the worktree) before the adapter's top-level `sandbox_can_reach_common_gitdir`
field is declared and the result is handed to REQ-662, which chooses
`exec.working_copy.strategy` from it. The headless
half of that evidence is REQ-664's `git-write-main` and `git-write-worktree`
probes (`.adlc/research/harness-probes/codex.json`); this REQ runs by hand
only the interactive half, which REQ-664 leaves `not-probed`. The result is
recorded in this spec and in the adapter file; neither `danger-full-access`
nor `approval_policy = "never"` is an acceptable default answer. A second
question rides on the same hand run: what does Codex do with an unmatched command, including the deny-tier spellings a token prefix cannot name (BR-10)? It is recorded as a measured fact and restores nothing.

What is deliberately lost on Codex, and said so in the README (plan §4):
honour-system read-only reviewers; the skills catalog budget (2 % of context
or 8 000 chars, past which Codex shortens descriptions and drops skills with a
warning); no `/sprint` Workflow engine; `$skill` rather than `/skill`
invocation; undocumented subagent nesting (the runner stays flat anyway);
undocumented transcript schema (REQ-660/P5); token-prefix allowlist
granularity; and, because the deny tier renders as `prompt`, an in-session
merge or deploy is a human confirmation for plain invocations (wrapped invocations rely on the sandbox); `git push`, `git branch` and every `git -C <path>` command are unmatched and behave as the measured unmatched default records; routine `allow` rules run outside the sandbox and the lint checks prefix and wrapper relations only; and deny-tier `prompt` rules match plain argv only.

Nothing that works today moves (plan Rule A). Claude Code's behaviour is
byte-identical after this REQ; `adlc agents render` with no `--harness` keeps
stamping `model:` in place.

## Business Rules

- [ ] BR-1: `harness/codex.yml` is the **only** place a Codex path, format name or binary name is written. Every renderer, the delegation installer, `/init`, doctor and README snippets read those values through the REQ-657 adapter loader; a literal `~/.codex` anywhere else in `tools/`, `partials/`, `agents/`, a `SKILL.md` or `install.sh` is a finding of REQ-666's `no-harness-path` lint (REQ-654 BR-13's narrower check until it lands); the project-relative `.codex/` and `~/.agents` spellings are held to the same rule by this REQ's AC-1 test, whose only exemption is the lane-check blocked-path list (`DEFAULT_BLOCKED_PATHS`, its test and `partials/lane-check.md`), which must name the directory it blocks. The adapter declares every field the REQ-657 schema requires, and the loader refuses an adapter with a missing or unknown key (informed by LESSON-716, LESSON-019).
- [ ] BR-2: `adlc agents render --harness codex` writes one TOML file per canonical `agents/<name>.md` into the adapter's `paths.agents.user`, from the same source files and tier config as the Claude render, with the tier config's Codex column resolved through the adapter's `tier_map` (`unverified` or a missing entry omits `model` rather than inventing one). The render is idempotent and atomic (a second run reports zero files changed), and `adlc harness render --check --harness codex` (the `render-currency:codex` check) fails when a rendered or hand-edited user-level file differs from what render would write. The adapter declares `agent_tool_restriction: none`, so per REQ-657 BR-4 every agent whose canonical `tools:` omits both Edit and Write gets the framework's restraint sentence as the **first line** of `developer_instructions`, identical in every such file; agents whose `tools:` includes Write or Edit, or have no `tools:` line, get no restraint line. No ETHOS prepend line is rendered: Codex declares `subagent_start_hook: yes` and the hook of BR-6 carries ETHOS to subagents (REQ-657 BR-4). If Open Question §6.8 shows the hook does not reach a subagent, the adapter flips `subagent_start_hook: no` and the framework renderer prepends the line — no Codex-specific code. The project-level `.codex/agents/` is never written by this REQ; the `--project-agents` opt-in is deferred by REQ-657 (plan M7). (informed by REQ-519 BR-1, REQ-519 BR-3)
- [ ] BR-3: The allowlist renderer's Codex target turns `templates/permissions.yml` into `.codex/rules/adlc.rules`. Every deny-tier entry becomes a `prefix_rule` with `decision="prompt"` in the committed `/init` render (REQ-657 BR-6, `deny_tier_render: {project: confirm}`) and `decision="forbidden"` only in the exec-engine render REQ-662 owns (`exec.deny_render: file`, keyed on `capabilities.deny: yes`, written to a file name distinct from `adlc.rules`; `adlc harness install` owns `adlc.rules`); the deny tier is not rendered at user scope (`deny_tier_render` has no `user` entry, i.e. `unsupported`); `allow` is never emitted for a deny-tier entry. A routine-tier entry becomes a `prefix_rule` with `decision="allow"` unless it is a proper token-prefix of, or a wrapper around, a deny-tier pattern. `["git", "push"]` and `["git", "branch"]` are omitted unconditionally on Codex, as `["git", "-C"]` is: a token prefix is position-sensitive and cannot express a force flag, `+refspec` or `-D` at any argument position (`git push origin +HEAD:refs/heads/x`, `git push origin --force`, `git branch foo -D`) and cannot name the variable `<path>` token of `git -C <path> <sub>`, so no probe or hand result restores them. Each is reported `inexpressible` in `accepted_fidelity` with the deny-tier pattern it overlaps, the adapter declares them never-restore (REQ-657 allows an adapter-declared never-restore), no `-C` rule of any decision is rendered, and `git -C <path> <sub>` falls to Codex's handling of an unmatched command, whose measured behavior BR-10 records. A restoration path (REQ-664's `ask-tier-deny` probe, sub-variant `deny-under-allow`, `pass` at `codex.json`'s `harness_version` AND the by-hand `strictest-wins` case of BR-10) applies only to a future routine entry whose every deny-tier spelling is a same-position prefix, as verified by the lint; `wrapped-allow` is not a restoration route on Codex, because a literal `<path>` cannot generalise. Deny-tier `prompt` rules match plain argv only. A deny-tier command inside shell control flow, a substitution, an env-assignment prefix or `bash -lc '<script>'` is unmatched; what stops it is the sandbox, not the rule, and only while `network_access` is off.
