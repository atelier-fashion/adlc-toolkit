## Description

This is P7b of `.adlc/research/multi-harness-plan.md` (revision 2): the one
move that REQ-654 (P0) deliberately excluded. REQ-654 makes the toolkit's home
a variable, `ADLC_HOME`, whose default is `$HOME/.claude`, and promises that
with the default nothing on disk moves (the plan's Rule A). This REQ is the
**opt-in** move for a machine that wants the toolkit's state out of
`~/.claude`: `install.sh --migrate-home <dir>` relocates every piece of
machine state the toolkit owns, re-stamps every generated file that carries
its old location, persists the new home so every later session resolves it,
and `install.sh --migrate-home --back` reverses the whole thing exactly.

The adversary pass on the plan (§8 findings C1, M2, M8) is the reason this is
its own REQ rather than a flag on P0, and it fixes what a safe migration must
hold:

- **C1 / M2 — stale vendored partials.** Every consumer repo carries
  `.adlc/partials/id-alloc.sh`, and an un-synced copy still spells the counter
  as the literal `$HOME/.claude/.global-next-<kind>`. If the counter moved and
  the literal kept resolving to a *second* file, two allocators would mint from
  two counters, and the plan's "one counter under one lock" would be gone. So
  the migration **refuses to run while `adlc doctor consumer-sync` reports any
  consumer whose vendored partials are not current**, and leaves
  compatibility symlinks at the old counter and config paths so every *other*
  reader of the literal path (a pre-REQ-654 `adlc doctor counters`, a human
  `cat`) still sees the one value; a stale allocator never reaches the counter
  because its lock loop aborts first. The lock dirs
  cannot be shared that way (BR-6 says why), so the old lock paths are
  tombstoned instead: a stale allocator fails loud in its own five-second
  budget rather than allocating under a split lock.
- **M8 — no rollback, config and venv hazards.** `install.sh` scaffolds a
  fresh config with delegation off, so a migration that lost the config would
  silently switch delegation off (BUG-205's shape); the delegation venv is not
  relocatable (its scripts and `pyvenv.cfg` embed the absolute path); the
  `~/bin` wrappers and the launchd plist are stamped with the old home. The
  migration therefore stages the complete new home first, flips in one step
  under the allocation locks, keeps a backup until `--back` or an explicit
  prune, and offers `--dry-run`.

What moves is exactly REQ-654's `HomeResolution` set minus the two Claude Code
mounts: machine config, the three ID counters and their lock dirs, the
own-reservation ledger, the delegation venv, the skills-only view, and the
launchd helper script. `~/.claude/skills` **always stays the clone-root
symlink** (the REQ-610 fence fallback `~/.claude/skills/partials/<name>.sh`
has to resolve on every machine) and `~/.claude/agents` stays where it is.
`~/.claude/CLAUDE.md` and `~/.claude/settings.json` are Claude Code's files,
not toolkit state, and the migration never writes them. Doctor gains a check that verifies
the migrated layout end to end, so the state of the machine is visible after
the move and after the reversal.

## System Model

### Entities

| Entity | Field | Type | Constraints |
|--------|-------|------|-------------|
| HomeState | current_home | path | the resolved `ADLC_HOME` (REQ-654 `HomeResolution.adlc_home`) |
| HomeState | default_home | path | `$HOME/.claude`; the only place compatibility symlinks, lock tombstones and the persisted setting may live |
| HomeState | migrated | boolean | true iff `current_home != default_home` and the persisted setting names `current_home` |
| MovedItem | kind | enum | `config` (`adlc/config.yml`), `counter` (`.global-next-req/-bug/-lesson`), `lockdir` (`<counter>.lock.d`), `ledger` (`.adlc-own-reservations`), `venv` (`delegate-venv`), `view` (the REQ-654 SkillsView), `launchd-helper` (`delegate-launchctl-setenv.sh`) |
| MovedItem | old_path | path | under `default_home` |
| MovedItem | new_path | path | under `<dir>` |
| MovedItem | transfer | enum | `move` (byte-identical, verified by checksum) / `rebuild` (venv only: recreated at `new_path` from `tools/delegate/requirements.txt`) / `regenerate` (view and launchd helper: rebuilt by the installer the way `install.sh` builds them) |
| MovedItem | compat | enum | `symlink` (`config`, `counter`: old path becomes a symlink to new path) / `tombstone` (`lockdir`: old path made un-lockable) / `none` (`ledger`, `venv`, `view`, `launchd-helper`) |
| StampedFile | path | path | `$HOME/bin/adlc`, `$HOME/bin/adlc-read`, `$HOME/bin/adlc-write`, `$HOME/bin/extract-chat`, `$HOME/Library/LaunchAgents/com.adlc-toolkit.delegate-setenv.plist`, the rc file carrying the `# >>> adlc-toolkit (REQ-519) >>>` block |
| StampedFile | carries | string | the absolute home path (or `$HOME/.claude` expansion) the file embeds today; after migration it embeds or resolves `current_home` and nothing else |
| PersistedSetting | rc_line | string | `export ADLC_HOME="<dir>"` inside the existing REQ-519 marker block of the login shell's rc file; absent when not migrated |
| PersistedSetting | pointer | file | a file under `default_home` naming `<dir>`, read by home resolution when `ADLC_HOME` is unset, so a session that never sourced the rc file (GUI-launched Claude Code, launchd) resolves the migrated home; exact name is an architecture decision |
| Backup | path | path | under `default_home`, timestamped; holds a byte-identical copy of every `move`d item and every `StampedFile` as they were before the flip |
| Backup | retained_until | enum | `--back` moves the **live** items back and removes it (the backup is removed, not restored); the backup is read only by BR-4's flip rollback; `--migrate-home --prune-backup` removes it; nothing else does |
| MigrationPlan | actions | list | one line per MovedItem, StampedFile, compat entry, PersistedSetting write and `~/.agents/skills` re-point, in execution order; `--dry-run` prints it and executes none |
| MigrationPlan | preflight | list | the refusal checks of BR-3, each with its verdict |

### Events

| Event | Trigger | Payload |
|-------|---------|---------|
| migration_refused | any BR-3 preflight check fails | the check, the evidence (stale repo names, held lock, foreign entry in `<dir>`), the remediation; nothing on disk changed |
| migration_staged | every `move`/`rebuild`/`regenerate` item exists and verifies under `<dir>` | per-item checksum or rebuild verdict |
| migration_flipped | the single flip step completed under the three allocation locks | old → new path per item, compat entries written, pointer and rc line written, shims and plist re-stamped, `~/.agents/skills` re-pointed |
| migration_reversed | `--back` completed | the same list in reverse; backup consumed |
| home_layout_checked | `adlc doctor` | PASS / FAIL / SKIP with every MovedItem, StampedFile and compat entry named on FAIL |

_Permissions: not applicable — single-user machine tooling. Section omitted deliberately._

## Business Rules

- [ ] BR-1: `install.sh --migrate-home <dir>` moves exactly the toolkit-owned machine state: the machine config, the three counters, their lock dirs, the own-reservation ledger, the delegation venv, the skills-only view and the launchd helper (the `MovedItem` kinds). It never moves, edits or deletes `~/.claude/skills`, `~/.claude/agents`, `~/.claude/CLAUDE.md`, `~/.claude/settings.json`, the telemetry log under `~/Library/Logs`, or anything under `~/.claude` the toolkit did not create. After the move `~/.claude/skills` still resolves to the clone root and `~/.claude/agents` to `<clone>/agents`, exactly as REQ-654 BR-3 and BR-6 require, because the REQ-610 fence fallback and Claude Code's own mount depend on them. `<dir>/skills` and `<dir>/agents` are created as symlinks to the clone root and `<clone>/agents`, exactly as REQ-654 AC-2 creates them for an overridden home; they are part of the migrated home for BR-9's removal rule and BR-12 checks they resolve. (informed by REQ-610, REQ-519)
- [ ] BR-2: `<dir>` must be an absolute path that is not `$HOME/.claude`, not inside it, and not inside the clone; it may be absent, or an existing directory that is empty or already holds only a previous toolkit home. Any other content in `<dir>` is a refusal naming the foreign entry, never a merge. A relative or empty `<dir>` is rejected with a message naming the flag, the same posture REQ-654 BR-2 takes for a bad `ADLC_HOME`.
- [ ] BR-3: The migration is **preflighted** and refuses, with nothing on disk changed, when any of the following holds: `adlc doctor consumer-sync` reports a `stale` or `unverified-baseline` consumer (the first is the hazard that made relocation unsafe, plan findings C1 and M2; the second means currency cannot be proven, BUG-204); `ADLC_HOME` is set in the environment to anything other than the current home or `<dir>`; the pointer file names a home other than `<dir>` (the machine is already migrated elsewhere; run `--back` first); a counter lock dir is held and cannot be acquired within the id-alloc budget; `<dir>` is not the current home **and** a previous migration's backup exists and `--prune-backup` was not given (a repair of the current home, BR-11, never trips this); the delegation venv exists but the machine cannot rebuild it (no `python3`, or the pip install into the staged venv fails); or `<dir>` fails BR-2. Each refusal prints the evidence and a copy-pasteable remediation (for a stale consumer: the per-repo `/template-drift` command `consumer-sync` already prints). (informed by LESSON-572, BUG-204, LESSON-441)
- [ ] BR-4: The migration is **staged then flipped**. Everything under `<dir>` is built and verified first: `move` items are copied and checksum-compared, the venv is rebuilt from `tools/delegate/requirements.txt` and probed the way `install.sh` probes it (the interpreter rule of REQ-609), the view is regenerated. Once the three locks are held and before any rename, every `move` item (counters, ledger, config) is re-compared against its live file and re-copied on mismatch, and the BR-10 backup copy of those items is taken at that moment; a counter advanced between staging and the flip is never left behind. The venv rebuild performs only the venv-creation and pip steps of `tools/delegate/install.sh`, never its CLAUDE.md, settings.json, launchctl-setenv or log-dir steps. Only then does one flip step run **inside the three allocation lock dirs**, acquired with the same `mkdir` protocol `partials/id-alloc.sh` uses: each old counter and config path is replaced by its compatibility symlink in a single rename, the lock tombstones are written, the pointer and rc line are written, shims and plist are re-stamped, and `~/.agents/skills` is re-pointed; the pointer and rc line are written **before** the old lock dirs are released and made un-lockable, and the flip holds the `<dir>` lock dirs as well as the old ones, so no allocator resolving either home runs during the flip. No allocator can observe a moment with no counter or with two live counter files. If any step of the flip fails, the flip is undone from the backup before the command exits non-zero, and the message names the step. (informed by REQ-546, REQ-519 BR-2, LESSON-014)
- [ ] BR-5: **Compatibility symlinks at the old counter and config paths.** After the flip, `$HOME/.claude/.global-next-req`, `-bug`, `-lesson` and `$HOME/.claude/adlc/config.yml` are symlinks to the files under `<dir>`. A stale `id-alloc.sh` never reaches the counter (its lock loop aborts first, BR-6); the counter links exist for every *other* reader of the literal path — `adlc doctor counters` from a pre-REQ-654 checkout and a human `cat` — and are safe because no shipped copy refuses a symlinked counter (`[ -f ]`, `cat` and `>` follow symlinks). The machine-config loader follows a live symlink and refuses only a dangling one, so delegation stays exactly as configured and is never recreated as `enabled: false` (plan finding M8, BUG-205). The ledger gets **no** link: every shipped writer (`id-alloc.sh`) and reader (`partials/id-recheck.sh`) refuses a symlinked ledger by design (LESSON-014), so a link would be refused and a stale consumer's recheck degrades to the documented advisory collision behaviour instead.
- [ ] BR-6: **Old lock paths become un-lockable, never shared.** A `mkdir` lock is only mutually exclusive between callers that `mkdir` the same path, so no symlink can make `$HOME/.claude/.global-next-<kind>.lock.d` and `<dir>/.global-next-<kind>.lock.d` one lock. The required outcome: after the flip, every `id-alloc.sh` ever shipped that still carries the old lock literal aborts without allocating, inside its own lock budget, with a message on stderr (the allocator's lock-acquisition error, `failed to acquire <lock> after 50 retries — aborting to avoid duplicate id`, or its symlink refusal). The mechanism (a regular-file tombstone at the old lock path, or a symlink, which the allocator refuses instantly with its TOCTOU message) is an architecture decision recorded per BR-14. This is the fail-loud outcome LESSON-014 and REQ-416 chose over a silent split. The request's "keeps allocating from the one counter under the one lock" is met for every **current** consumer (BR-3 guarantees there are no others at migration time) and is converted into a loud refusal for a consumer that goes stale afterwards; it is not met silently for anyone. Doctor reports a directory at an old lock path as evidence of a stale allocator (BR-12).
- [ ] BR-7: **Every stamped file is re-stamped**, derived from the install-time facts the way REQ-519 BR-3 requires: the `~/bin/adlc` shim resolves the delegation interpreter under the current home, not under `$HOME/.claude`; the `~/bin/adlc-read`, `adlc-write` and `extract-chat` wrappers exec `<dir>/delegate-venv/bin/python3`; the launchd plist points at `<dir>/delegate-launchctl-setenv.sh` and is validated with `plutil -lint`, unloaded and reloaded the way REQ-522 BR-8 migrates a plist; the two rc marker blocks keep their `PATH` lines (`$HOME/bin` does not move); the REQ-519 block gains the BR-8 line. `grep -r '/.claude/delegate-venv'` over `~/bin` and `~/Library/LaunchAgents` finds nothing after migration; after `--back` it finds exactly what a fresh install writes. (informed by REQ-519, REQ-522)
- [ ] BR-8: **The persisted setting is reachable without an rc file.** The migration writes `export ADLC_HOME="<dir>"` inside the existing REQ-519 marker block of the login shell's rc file (marker-guarded, idempotent, atomic — REQ-519 BR-1, BR-2) **and** a pointer file under `$HOME/.claude` naming `<dir>`. REQ-654's home resolution gains one step: `$ADLC_HOME` if set, else the pointer file if present, else `$HOME/.claude`. A GUI-launched Claude Code session, a launchd job and a `/bin/sh` fence with no environment all resolve the migrated home through the pointer; a session with `ADLC_HOME` set to a different directory is a conflict that doctor reports and `adlc` refuses, never a silent fall-through; a pointer naming a directory that does not exist fails loud with a message naming the pointer and the missing directory, never a fall-through to `$HOME/.claude` (consistent with REQ-654 BR-2's posture for a bad `ADLC_HOME`). With no pointer and no variable, resolution is byte-identical to REQ-654. (informed by LESSON-395)
- [ ] BR-9: `install.sh --migrate-home --back` **reverses exactly**: it reads the pointer to find the current home, acquires the locks, moves every `move` item back under `$HOME/.claude` replacing the compatibility symlinks and lock tombstones with the real files, rebuilds the venv at `$HOME/.claude/delegate-venv`, regenerates the view there, re-stamps every stamped file to the default layout, removes the rc line and the pointer, re-points `~/.agents/skills`, and removes `<dir>` only when nothing but the migrated home remains in it. It runs under the BR-3 lock, `ADLC_HOME`-conflict and venv-rebuild checks, plus: the pointer must name an existing home and the backup must exist (a stale consumer is harmed by the forward move, not the reversal) and the same stage-then-flip discipline as BR-4, with one substitution: `--back` takes its own timestamped copy of the live `<dir>` `move` items under the locks, undoes a failed reverse flip from **that** copy, never from the forward backup, and removes both copies on success. After `--back`, every `move` item is byte-identical to the live file that was under `<dir>` at the moment `--back` acquired the locks (the backup is never restored by `--back`), and `adlc doctor` reports the same verdicts it reported before the migration.
- [ ] BR-10: **Backup and dry-run.** Under the locks, immediately before the flip, every `move` item is copied; every stamped file is copied before the locks are taken, into a timestamped backup directory under `$HOME/.claude`, and the backup is named in the final summary. The backup is consumed by `--back` or removed by `--migrate-home --prune-backup`; nothing else deletes it, and a migration to a different `<dir>` refuses while it exists (BR-3). `--migrate-home <dir> --dry-run` prints the full `MigrationPlan` — every preflight verdict and every action in execution order, naming the old and new path of every item — and changes nothing: a checksum of `$HOME/.claude`, `$HOME/bin`, `$HOME/Library/LaunchAgents` and the rc file is identical before and after. (informed by REQ-519 BR-1)
- [ ] BR-11: **Idempotent and repair-capable.** `--migrate-home <dir>` on a machine already migrated to `<dir>` is a repair: it re-verifies every item, re-stamps anything that drifted (a shim rewritten by a plain `./install.sh`, a plist regenerated by `tools/delegate/install.sh --with-delegation`) and reports zero actions when healthy. Plain `./install.sh`, `--repair` and `--with-delegation` on a migrated machine honour the resolved home: they scaffold nothing under `$HOME/.claude`, they never replace a compatibility symlink with a scaffolded file, and the delegate installer builds its venv and wrappers against the resolved home. (informed by REQ-519 BR-1, BR-3)
- [ ] BR-12: **Doctor verifies the migrated layout end to end.** The check registry gains `home-layout` with REQ-519's pass/fail/skip semantics and copy-pasteable remediations: SKIP when not migrated (pointer absent and `ADLC_HOME` unset or equal to the default); otherwise PASS only when the pointer, the rc line and any `ADLC_HOME` in the environment agree, every `move` item exists under the current home, every compatibility symlink resolves to it and **no regular counter or config file remains at an old path**, every old lock path is un-lockable per the BR-6 mechanism and **no directory** exists there (a directory there is evidence of a crashed stale allocator or a removed tombstone), every stamped file carries the current home, the venv under the current home passes the REQ-609 interpreter probe, the view and `~/.agents/skills` resolve under the current home, `<current_home>/skills` and `<current_home>/agents` resolve to the clone root and `<clone>/agents` (BR-1), and `~/.claude/skills` still resolves to the clone root. A pointer naming a directory that does not exist is a FAIL (BR-8), not a SKIP. Every FAIL names the item and gives `./install.sh --migrate-home <dir>` (repair) or `--back` as the remediation. The existing `counters`, `pyyaml`, `launchctl`, `path-shims` and `delegate-gate` checks read the resolved home, so they pass on a migrated machine for the same reasons they pass on a default one. (informed by REQ-519 BR-4, BR-5, LESSON-395)
- [ ] BR-13: All new and changed shell is POSIX-sh, bash 3.2, zsh and dash safe and is executed under each by `partials/tests/run.sh`: no `case` inside `$( )`, no `\b` in `grep -E`, no bare `$<digit>`, no `local`, no `[[`, no `set -e` reliance across a fence, decimal normalization before arithmetic. New Python is stdlib only, because doctor must diagnose a half-migrated machine without the venv it is checking. Migration code reaches `$HOME/.claude` only through REQ-654's default-home helper, never a literal. (informed by LESSON-582, LESSON-395, LESSON-013, LESSON-335)
- [ ] BR-14: Documentation that states the install layout is updated in the same change: `README.md` (the migration section: what moves, what never moves, the backup, `--back`), `.adlc/context/architecture.md` (the stage-then-flip rule, the compat-symlink and lock-tombstone rules and why they differ, and the BR-6 mechanism chosen), `.adlc/context/conventions.md` (the home-resolution rule gains the pointer step: `$ADLC_HOME`, else the pointer, else `$HOME/.claude`), `tools/adlc/README.md` (`home-layout`), `CHANGELOG.md`. The architecture note says in one sentence why the counters get symlinks and the locks get tombstones, so the next author does not "fix" one into the other. (informed by LESSON-019)
- [ ] BR-15: `tools/lint-skills` and `partials/tests` gain fixtures for the migrated layout: a sandbox `HOME` migrated to a sandbox `<dir>`, under which the id-alloc harness allocates through the compatibility symlink from a **stale** copy of `id-alloc.sh` (fails loud on the tombstoned lock before touching the counter, and leaves the counter at the one value) and allocates normally from the current copy; and the lint check REQ-654 BR-13 adds still fires on a new `$HOME/.claude` literal in the migration code, which reaches `$HOME/.claude` only through REQ-654's default-home helper (BR-13). (informed by LESSON-012)

## External Dependencies

- No new external tools. `python3` (stdlib) for `adlc`; `python3 -m venv` and `pip` with network access to rebuild the delegation venv when one exists; `plutil` and `launchctl` on macOS for the plist, skipped-with-notice elsewhere as REQ-519 BR-6 already does.

## Assumptions

- A Python venv is not relocatable (its `bin/*` shebangs and `pyvenv.cfg` embed the absolute path), so the venv is rebuilt at the new home rather than moved, and the rebuild needs network access to the package index; a machine without it cannot migrate while a venv exists, and the preflight says so (BR-3). Pinning in `tools/delegate/requirements.txt` makes the rebuilt venv equivalent for the toolkit's purposes.
- No shipped `id-alloc.sh` refuses a symlinked **counter** file (`id-alloc.sh` refuses a symlinked lock dir and ledger, and `partials/id-recheck.sh` refuses a symlinked ledger, only), so the compatibility symlink at the counter path is readable and writable by every vendored copy in the field. A future hardening that refuses a symlinked counter must keep this REQ's contract or be shipped together with a `--back`.
- The consumers under `$ADLC_REPOS_ROOT` are the complete set of machine-local allocators, as REQ-654 and `partials/id-alloc.sh` already assume; an allocator elsewhere is outside both the consumer-sync gate and the tombstone's reach.
- `~/.claude/skills` keeps resolving to the clone root on every machine for at least this release (REQ-654's second open question, proposed resolution adopted here), so the fence fallback needs no compatibility handling from this REQ.
- id allocated with remote reservation (`degraded=0`); no degraded-allocation note required.

## Open Questions

- [x] The request asks that a consumer whose vendored partials still carry the old literals "keeps allocating from the one counter under the one lock". A `mkdir` lock cannot be shared across two paths by any symlink, and every shipped `id-alloc.sh` refuses a symlinked lock path, so that outcome is not achievable for a stale copy. BR-6 proposes the fail-loud alternative (lock tombstones: a stale allocator aborts in its own five-second budget and allocates nothing) and relies on BR-3's consumer-sync gate for "no stale copy exists at migration time". Is the loud refusal acceptable in place of silent sharing, or should a stale allocator be allowed to allocate under a separate lock with the counter value shared through the symlink (a split lock, which the plan's finding M2 names as the hazard)? **Resolved:** the loud refusal (BR-6) adopted; revisit at /architect.
- [x] Where the persisted setting lives for sessions that never source an rc file. BR-8 proposes a pointer file under `$HOME/.claude` read by home resolution before the default, which adds one step to REQ-654's `HomeResolution`. The alternative is `launchctl setenv ADLC_HOME` through the existing delegate helper, which is macOS-only and absent on a machine that never opted into delegation. Pointer file proposed; confirm, since REQ-654's resolution rule has to change with it. **Resolved:** pointer file (BR-8) adopted; revisit at /architect.
- [x] Whether a migrated machine should keep `~/.claude/adlc/config.yml` as a compatibility symlink at all, given BR-11 requires plain `./install.sh` to never re-scaffold it. The symlink protects a `tools/delegate` copy that predates REQ-654 (a consumer-vendored `adlc-read` does not exist, so the only such copy is an old toolkit checkout); if that case is out of scope the config needs no link and BR-5 shrinks to the counters. **Resolved:** keep the config symlink (BR-5 as written) adopted; revisit at /architect.

## Out of Scope

- Changing REQ-654's default (`$HOME/.claude`) or making migration the default for any install; a fresh `./install.sh` never migrates.
- Moving `~/.claude/skills`, `~/.claude/agents`, `~/.claude/CLAUDE.md`, `~/.claude/settings.json`, or the telemetry log; retiring the `~/.claude/skills` literal from fences (P1 `no-harness-path`).
- Migrating the harness-side renders (`~/.copilot`, `~/.codex`, `~/.gemini`, `~/.cursor`, `~/.agents/skills` beyond re-pointing it) — P2 onward owns those paths.
- Making stale vendored partials work under a split lock; the design converts that case into a loud refusal (BR-6) and the gate (BR-3) prevents it at migration time.
- Multi-user or shared-home machines, Windows, and migrating between two non-default homes in one command (a second migration goes through `--back` first, or is a repair when `<dir>` is the current home).
- Plugin manifests at the clone root (the other half of P7).
