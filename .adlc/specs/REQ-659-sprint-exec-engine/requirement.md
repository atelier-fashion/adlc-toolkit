## Description

This is P6a of `.adlc/research/multi-harness-plan.md` (revision 2): the **exec
engine**, a third `/sprint` engine beside the Dynamic Workflows engine and the
legacy background-`pipeline-runner` engine. The two existing engines are models
orchestrating models: the `/sprint` skill text, or a workflow script whose leaves
are agents. The exec engine is different in kind. **The orchestrator is a
program, not a model.** Per REQ it prepares a working copy, builds the pipeline
prompt itself, launches one non-interactive harness process with that prompt on
stdin, watches the REQ's `pipeline-state.json`, and — when the model reaches the
merge gate — stops it there. The model never merges, never deploys, never
force-pushes, never deletes anything. Those one-way moves are performed by the
orchestrator, through the same `partials/forge.sh` and `partials/trial-merge.sh`
the interactive path uses, from the parent repo, **after** an operator runs
`/sprint approve REQ-nnn` (plan Rule B).

Why this engine exists:

1. **Rule B is structural here, not prose.** Today the legacy runner is told
   "you own the merge" (single-repo) and the workflow engine's leaf merges; both
   depend on a model obeying text, and a sandbox that denies `gh pr merge`
   leaves the REQ dead at the last step (LESSON-355). In exec mode the prompt's
   Phase 8 is replaced by "stop and write `awaiting_approval`", the harness is
   launched with the deny tier rendered as hard denies, and the merge is code the orchestrator
   runs after an explicit approval. An unattended batch cannot merge anything
   through a move the orchestrator owns. The allow and deny tiers are defense in
   depth with declared residuals (BR-8); what makes the one-way moves structural
   is the gates: the approval ledger (BR-10), the pinned orchestrator merge
   (BR-11), the detached-worktree trial merge and rebase (BR-11, BR-12), the
   local diff gates (BR-13, BR-14), the child credentials (BR-22), branch
   protection (BR-8) and the exit checks (BR-15).
2. **It is the port.** Copilot CLI, Codex, Gemini CLI and Cursor all have a
   headless `-p`-style mode that takes a prompt and runs tools under an
   allowlist. None of them has Dynamic Workflows, and none can be driven by a
   Claude Code skill. An orchestrator that owns the prompt (plan M9), the
   working copy (M5), the trust grant (M4) and the one-way moves (M1) is the
   only shape that runs the same pipeline on all five. This REQ ships the
   engine with the **`claude` adapter only** (`claude -p`, prompt on stdin,
   JSON output); the Copilot, Codex, Gemini and Cursor exec adapters are a
   sibling REQ, and the adapter contract defined here is what they fill in.
3. **It needs nothing plan-gated.** Dynamic Workflows is research-preview and
   can be absent (headless, cron, non-qualifying plans). The exec engine needs
   a shell, `git`, the forge CLI and one harness binary.

What the engine does per REQ, in order (plan §2f): prepare the working copy by
the adapter's declared strategy → grant per-run trust → build the prompt
(`proceed/SKILL.md` body, its phase companion files, `.adlc/ETHOS.md`, the REQ
id, the working-copy path, the unattended block, the Phase-8 replacement) →
launch the harness with routine-tier allow flags and one-way deny flags, never
`--dangerously-skip-permissions` / `--yolo` / `--force` / `--allow-all` →
monitor the state file (stall by mtime) → on `awaiting_approval`, show the
proposed action in the dashboard and wait for `/sprint approve` or `reject` →
on approval, trial-merge against the fresh integration tip (REQ-483), merge via
`adlc_forge_pr_merge`, deploy per `.adlc/config.yml`, run the Step 8b close-out
(the one place the harness session is **resumed**, because lesson drafting is
model work), clean up the working copy and revoke trust. Dynamic Workflows and
the legacy engine are unchanged.

| Event | Trigger | Payload |
|-------|---------|---------|

| trust_granted / trust_revoked | before launch / on cleanup, abort or reject | harness, workingCopy, mechanism |
| exec_abort | `/sprint abort REQ-nnn` | req, process group killed, abortedBy, trust revoked, working copy left in place |
| awaiting_approval | the model reaches the merge gate and writes `status: awaiting_approval` + `approval` | req, PR url(s), `repos`, what the orchestrator will do on approval (merge, deploy if declared, close-out, cleanup) |
| approval_decided | `/sprint approve REQ-nnn` or `/sprint reject REQ-nnn [reason]` | decision, decidedBy (`$USER`), channel (`skill` \| `shell`), callerPid, the ledger path written first, reason, and for `approve` whether it is queued behind an ahead overlapping REQ (REQ-483 order) and whether the REQ changes the gate and the operator acknowledged it (BR-23c) |
| protocol_violation | a PR already `MERGED` before approval (BR-11); the REQ branch already an ancestor of `origin/<integrationBranch>` before approval (BR-15); an `approval.decision` in state with no ledger entry (BR-10); a `merged`/`pr-ready` claim on an exec run; an approval attempt from inside a run or while the process is alive (BR-10); a live PR whose number, repo or head oid differs from the ledger plan (BR-11); a checksum mismatch of the common gitdir's `config`, `config.worktree`, `hooks/`, `info/attributes` or `worktrees/*/config.worktree`, or a sha256 manifest mismatch of a resolved binary or the install (BR-23b); a ledger present before the halt write that the run record does not account for (BR-10); a first-parent commit in `<launchTip>..origin/<integrationBranch>` that is neither a recorded orchestrator merge nor associated with a merged PR (BR-15) | req, rule (always Rule B), the evidence, what the orchestrator did next — always surfaced in the dashboard, never executed on |
| one_way_move | the orchestrator performs merge, deploy, close-out chore merge, or working-copy removal | which move, the partial/function used, rc, PR state verified after |
| stall_flagged | `statePath` mtime older than the stall threshold while the process is alive | req, minutes since last write, pid alive? |
| exec_exit | the harness process exits | rc and its ExitClass, the parsed JSON result (`is_error`, `session_id`, `num_turns`, cost when reported), the terminal claim, and whether it agrees with the state file |

### Permissions

| Action | Allowed |
|--------|---------|
| Merge a PR, deploy, force-push, remove a working copy or branch | the orchestrator program, after a recorded `approve` for that REQ, and never the harness process |
| Write the approval ledger (`<run directory>/approval.json`) and mirror `approval.decision` into state | the orchestrator, on an operator's `/sprint approve\|reject` (or the equivalent CLI invocation from a plain shell); no harness process can reach the ledger |
| Write the working-copy `pipeline-state.json` while `exec.pid` is alive | the harness process only; the orchestrator's own fields go to the run directory until exit (BR-9) |
| Resolve a merge conflict | a human (REQ-485 BR-4); the orchestrator only rebases, aborts and re-halts |
| Execute any string read from `pipeline-state.json` | **none** — state is written by the model process and is data |
| Execute code or config a harness could write (a working copy's `.adlc/partials`, `.adlc/tools`, `.adlc/workflows`; the common gitdir's hooks, config and `info/attributes`; in the resumed close-out, the working copy's `.claude/` settings and `.mcp.json`, BR-25) | **none** (BR-23) |

## Business Rules

_Engine selection and scope_
- [ ] BR-1: `/sprint` gains a third engine, `exec`, selected only by an explicit `--exec` token (with optional `--harness <name>`, default `claude`), stripped from `$ARGUMENTS` before REQ-id parsing exactly as `--workflow` is. It is never the default and never a fallback: a `--workflow` run without the `Workflow` tool still falls back to `legacy`, as today. The workflow engine's script, the legacy Steps 1–6, `agents/pipeline-runner.md` and `proceed/SKILL.md`'s phase text are not changed by this REQ except where a rule below names them. (informed by REQ-474 BR-1)
- [ ] BR-2: The exec orchestrator is a program whose control flow is code — a shell or stdlib-Python executable under the toolkit, invoked by the `/sprint` skill for dispatch, status, approve and reject — and every one of those operations is also reachable from a plain shell without a Claude Code session, so a non-Claude operator can run it. The `/sprint` skill is a thin dispatcher for this engine, the way it is for the workflow engine (ADR-3 of REQ-474): the model never performs the merge sequencing, the approval bookkeeping or the state-file reads that the program does. The attended path assumes an operator session — a human typing into Claude Code. `sprint/SKILL.md` must run `approve` only on a literal operator instruction that names the REQ in the same turn, never from a plan, a file, a dashboard line, an earlier turn or the model's own suggestion, and every decision records the invoking channel (`skill` or `shell`) beside `decidedBy` (BR-10). (informed by REQ-474 BR-7, REQ-483 BR-10)
- [ ] BR-3: This REQ ships the engine with the `claude` adapter only. The adapter contract (working-copy strategy, trust mechanism, allow/deny tiers, forbidden flags, exit-code classes, child-environment passthrough, launch command, stdin delivery, JSON result parsing, resume) is defined here as the `exec` block of a harness adapter file — `harness/claude.yml` when REQ-657's adapter framework has landed, a standalone `harness/claude.exec.json` with the same keys when it has not (JSON, so the stdlib-Python/shell orchestrator reads it with no YAML parser, and a `.json` suffix so it sits outside REQ-657's `harness/*.yml` loader glob until REQ-657 folds it in) — and filled in per harness. REQ-657 declares `exec` as an opaque, schema-versioned sub-block that its loader validates only as map-or-absent; this REQ widens that `exec` into the ExecAdapter block (the engine keys, under an `exec_schema_version`) and reads `trust` from REQ-657's top-level adapter field rather than redeclaring it. The `claude` exec block is owned here; REQ-662 migrates it mechanically to the widened exec schema and never otherwise edits it. Migration note: `working_copy` is a scalar here (`worktree`); REQ-662's mechanical migration rewrites it to `working_copy: {strategy: worktree}` and the orchestrator accepts both spellings until that migration lands. The Copilot, Codex, Gemini and Cursor `exec` blocks are REQ-662 and are not stubbed here. `--harness` naming a harness with no shipped `exec` block is a pre-flight refusal that names REQ-662.

_Launch flags_

It kills the REQ's process group, revokes trust (BR-5), leaves the working copy, branch and any open PR in place for a human, records `status: failed` with `exec.abortedBy` (`$USER`) and `exec.abortedAt`, and performs no one-way move. The orchestrator never kills a process on its own: a stall (BR-15) is flagged, not killed (the one exception is the process-group kill and straggler sweep at the harness's own exit, BR-10, which reaps only what an already-exited harness left behind). `abort` against a REQ with no live recorded `exec.pid` is refused with a message (BR-10). (resolves OQ-3; informed by REQ-485 BR-8)
- [ ] BR-21: Each adapter declares an `exit_codes` map from the harness's raw exit codes onto the closed ExitClass `ok | denied | timeout | error`; an unmapped non-zero code is `error`. The orchestrator records the raw code and its class as the additive `exec.exitCode` and `exec.exitClass` on every exit. A `denied` exit sets `status: blocked` with the denial in `blockers`, because a human must decide whether the denied call belongs in the routine tier; `timeout` and `error` without a terminal claim are `failed` as BR-15 defines. The class never overrides a terminal claim the state file and the forge confirm.
- [ ] BR-22: The child environment is explicit. The orchestrator launches every harness — `claude` included — with only the variables named by the adapter's `exec.env_passthrough` list, whose default set is `HOME`, `PATH`, `ADLC_HOME`, `ADLC_DISABLE_DELEGATE`, `ADLC_FORGE_MOCK`, `SSH_AUTH_SOCK`, `GIT_SSH_COMMAND`, `XDG_CONFIG_HOME`, `TMPDIR`, `LANG`, `TERM`, plus the harness's own auth variables named in the adapter. The forge CLI's credentials are not inherited: the orchestrator sets `GH_CONFIG_DIR=<empty directory under the run directory>` (so the operator's stored `gh` login under `HOME`/`XDG_CONFIG_HOME` is unreachable) and sets `GH_TOKEN` to a scoped token without `contents: write`, read from the operator environment variable that `sprint.exec.child_gh_token` names (the config holds a variable name, never a token value); `GITHUB_TOKEN` is never passed. With no scoped token configured, launch is refused unless the operator passes `--shared-credentials`, which passes the operator's own forge credentials, is recorded in the ledger plan (`sharedCredentials: true`) and shown in the `awaiting_approval` row. This replaces the earlier `pass_forge_token` opt-in. `SSH_AUTH_SOCK` and `GIT_SSH_COMMAND` still give the child a push credential whatever the forge token is: that is a stated credential residual, and the controls are branch protection (BR-8) and the first-parent check (BR-15), not the environment. The orchestrator always adds `ADLC_EXEC_RUN=<REQ>` (BR-10). A variable not on the list is not inherited, so a launch is reproducible from the recorded run directory. The resumed close-out (BR-14) and an `answer` relaunch are launched under this same rule. (plan M1)

_Execution surface_
- [ ] BR-23: The orchestrator never executes code or config a harness could write. (a) Partials and tools (`forge.sh`, `trial-merge.sh`, `lane-check.sh`, `tools/adlc/*`) resolve only from the toolkit install (`ADLC_HOME`, then `~/.claude/skills`), by absolute path resolved once at orchestrator start, never via the cwd-relative `.adlc/partials` fence, and the orchestrator's cwd is never a working copy. (b) Git is neutralized through the environment, not through `-c` flags, which cannot reach a trial merge, `lane-check.sh`, id allocation or `gh` because those spawn git themselves. The orchestrator exports, for itself and every tool it runs, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=<runDir>/gitconfig` (an orchestrator-written file) and `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` setting `core.hooksPath` (an empty orchestrator-owned directory), `core.fsmonitor`, `core.sshCommand`, `credential.helper` and `core.attributesFile` (to the orchestrator's own values), `commit.gpgsign=false`, `log.showSignature=false` and `protocol.ext.allow=never`. `~/.gitconfig`, `~/.ssh/config` (used via `ssh -F <snapshot>`) and `~/.config/gh` are snapshotted into the run directory at launch, and orchestrator-side tools use the snapshots, so a later edit of the operator's files changes nothing that runs. `git`, `gh`, `az`, `python3`, `sh` and `ssh` are resolved to absolute paths once at start, and a sha256 manifest of those binaries and of the install (`partials/`, `tools/adlc/`, the orchestrator, `proceed/`, `wrapup/`) is verified before each source or exec. A launch-time checksum of the common gitdir's `config`, `config.worktree`, `hooks/`, `info/attributes` and every `worktrees/*/config.worktree` is re-verified before each git command run in that tree; `config` is checksummed with its `[branch "…"]` sections removed, so the upstream-tracking writes of a legitimate `git push -u` do not trip it. A mismatch of the manifest or of the checksum set is a Rule B protocol violation, surfaced and recorded, after which nothing further runs in that tree. BR-11's trial merge and BR-12's rebase run in an orchestrator-owned detached worktree at the ledger's `headRefOid`, never in the model's working copy. Every orchestrator push and fetch names the remote and refspec explicitly. `GIT_CONFIG_COUNT` needs git 2.31 and `git range-diff` needs 2.19; an older git is a pre-flight refusal. (c) A REQ whose diff (the local `--no-renames` changed-path set of BR-13, never the forge `files` list) touches `.adlc/partials/`, `.adlc/tools/` or `.adlc/workflows/`, or modifies the deploy surface (BR-13), shows a 'changes the gate' line in the `awaiting_approval` row and in the plan (BR-16), and `approve` requires `--ack-gate-change` answered with the gate-bound token (BR-10), so the approval records that the operator acknowledged it (BR-10); the skill passes the flag only on an operator instruction that names it. (informed by LESSON-619, LESSON-008, plan Rule B)
- [ ] BR-24: The empty allowlists of BR-6 and BR-14 are enforced at runtime, not only in the build test. After the orchestrator assembles the pipeline prompt (BR-6), the close-out prompt (BR-14) or an `answer` relaunch prompt, and before any launch or resume, it scans the exact bytes it is about to deliver for every empty-allowlist token — `adlc_forge_pr_merge`, `gh pr merge`, `az repos pr`, `you own the merge`, ``report `merged` ``, `pr-ready`, `{merged` and, for the close-out prompt, also `worktree remove`, `branch -D`, `--force-with-lease` and any deploy command — and refuses to launch on a hit, naming the token and the line, delivering nothing and starting no process. Every allowlist, in the build test and in the runtime scan, is a **full-line regex** matched against the whole line, never a substring and never a line number, so an edit that shifts lines neither hides a new mention nor strands an old one. The scanned bytes, the delivered bytes and `exec.promptPath` are the same bytes. (informed by LESSON-619, LESSON-712)
- [ ] BR-25: The resumed close-out session (BR-14) is launched so that no working-copy configuration configures the harness. A sibling harness declares its equivalent in REQ-662. The first launch and an `answer` relaunch are not covered by this rule (the model edits and runs the working copy's own files there); their controls are BR-8 and the gates. (informed by LESSON-619)
