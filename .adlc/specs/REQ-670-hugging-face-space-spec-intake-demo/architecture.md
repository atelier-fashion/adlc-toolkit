# REQ-670 Architecture: Hugging Face Space for spec intake

## Approach

A **static** Hugging Face Space (`sdk: static`) whose page calls the Anthropic
Messages API **directly from the visitor's browser**. No server code runs. The
Space source lives in a new top-level `space/` directory:

```
space/
├── README.md          # the Hugging Face Space card (YAML front matter: sdk: static)
├── index.html         # the page: disclosure, model id, key input, source input, result
├── style.css
├── config.json        # BR-9: { "model": ..., "max_tokens": ... } — configuration, not code
├── intake.js          # pure core: budget, redaction, request, response parsing, error classes
├── app.js             # DOM wiring only: textContent rendering, download, sample display
├── sample.js          # SampleRun: a synthetic input and its output, shown with no key
├── toolkit-data.js    # GENERATED by build.mjs from the toolkit — never edited by hand
├── build.mjs          # reads the toolkit, writes toolkit-data.js; --check fails on drift
└── tests/*.test.js    # node:test, zero dependencies
```

Data flow for a live run: `app.js` reads the source and the key from the page,
calls `runIntake({ source, apiKey, config, toolkit, fetchImpl: fetch })` in
`intake.js`, and renders the returned object with `textContent` only. `runIntake`
checks the budget, redacts, segments, builds one Messages request with a forced
tool call, sends it to the one fixed endpoint, and parses the tool input into
`{ requirement_md, gaps, redaction_count, toolkit_version }` or returns
`{ error: { class, message } }`.

## Key decisions

### ADR-1: Browser-side static Space, not a Gradio server (resolves Open Question 1)

The key goes from the visitor's browser straight to `api.anthropic.com` with the
`anthropic-dangerous-direct-browser-access: true` header. It never reaches a Space
process, so there are no Space logs, disk or persistent storage it could land in.
BR-1 then holds by construction on the server side and only has to be proven for
the browser code, which is small and testable.

A Gradio Space would pass the key through a Python process on Hugging Face's
hardware. Proving it never reaches a log there means trusting Gradio's request
handling, its queue, its analytics and Hugging Face's log capture. It also adds a
Python dependency set that `python3 -m pytest tools` would have to skip.

**Rationale:** the spec calls key handling "the core of the design" and asks for a
guarantee that can be proved. Moving the key off the server is the strongest such
guarantee available. The cost is CORS and browser exposure. The page sets a strict
Content-Security-Policy (`connect-src 'self' https://api.anthropic.com`, `script-src 'self'`,
no inline script), which limits where a key could be sent even if the page were
compromised. That also enforces BR-6's "which endpoint it calls" in the browser
itself, not only in code.

### ADR-2: Pure core plus a thin DOM layer, tested with `node:test`

`intake.js` holds every rule (budget, redaction, request shape, parsing,
error classification, key scrubbing) as pure functions with an injected `fetchImpl`.
It works as a classic browser script (a global `AdlcIntake`) and as a CommonJS
module under Node (`module.exports`), so it is tested directly. `app.js` touches
the DOM and does nothing else. It never uses `innerHTML`, `localStorage`,
`sessionStorage`, `indexedDB`, `document.cookie` or `console`. A structural test
pins that, because a DOM layer cannot be unit-tested without a DOM library, and
adding one would break the zero-dependency rule.

This follows the `workflows/tests/` precedent: Node's built-in runner, no package
manager, run as `node --test 'space/tests/*.test.js'`.

### ADR-3: Toolkit content is generated into the Space, never hand-copied (BR-3)

`space/build.mjs` reads, from the toolkit checkout it sits in:

| Source | Extracted |
|---|---|
| `templates/requirement-template.md` | the whole template text, and its `## ` headings |
| `spec/SKILL.md` | the intake gap rules, between new `<!-- intake-gap-rules -->` / `<!-- /intake-gap-rules -->` markers |
| `partials/intake.sh` | `ADLC_INTAKE_SEGMENT_LINES`, `ADLC_INTAKE_MAX_SEGMENTS`, the redaction regex in `adlc_intake_redact`, and the section exclusions in `adlc_intake_sections` |
| `README.md` | the two `claude plugin …` install lines (REQ-669) |
| `VERSION` | the toolkit version |

It writes them into `space/toolkit-data.js`, which is committed, because that file
is what the Space serves. `node space/build.mjs --check` regenerates in memory and
exits 1, naming each differing field, when the committed file differs. A test runs
`--check`, and a mutation test proves a changed template fails it (AC-5). This is
the `tools/adlc/agents_render.py --check` precedent (render plus drift check).

The POSIX ERE regex is split into its top-level alternatives, and each is translated
to a JS `RegExp` by a fixed table (`[[:space:]]` → `[ \t\v\f\r]`, `[^[:space:]]` →
`[^ \t\n\v\f\r]`). The build refuses to emit when any `[:class:]` survives
translation, so a new POSIX class in the chain fails the build rather than producing a
regex that silently matches nothing. `intake.js` then runs the chain the way sed does:
one line at a time, taking at each position the longest match any alternative gives
(POSIX leftmost-longest). A single JS regex would cross line breaks and take the first
alternative that matches, which is not the same chain (Phase 5 finding). A test runs
the real `adlc_intake_redact` under `sh` on the same inputs and requires identical output.

Two Space files restate toolkit facts for people and stay hand-written: the card
(`space/README.md`) shows the install commands and the line budget, and the sample's
output follows the template. Both are pinned by `space/tests/page.test.js` against
`toolkit-data.js`, so they are test-enforced rather than generated.

The gap rules are prose, so the Space passes them to the model verbatim in the
system prompt. Adding the markers is the only change to `spec/SKILL.md`. The
markers sit inside Step 1.4's numbered list as indented HTML comments, so the
rendered skill is unchanged.

**Pinned version:** the check compares against the toolkit files in the same
checkout. BR-13 has the Space rebuilt from a tagged release, so running the build
at a tag makes the pinned version the tag's. `RELEASING.md` gains the steps.

### ADR-4: One forced tool call returns structured output

The request declares one tool, `record_intake`, whose `input_schema` is
`{ requirement_md: string, gaps: [{ section, severity: enum[blocking, assumption], question, justification }] }`,
and sets `tool_choice: { type: "tool", name: "record_intake" }`. That gives
schema-shaped output without parsing free text. `parseResult` still validates
everything, because model output is untrusted (BR-6). It drops a gap with an
unknown severity or an empty question, rejects a non-string `requirement_md`, and
makes the result well-formed deterministically:

- any template `## ` heading missing from `requirement_md` is appended with a
  "Not covered by the source" line (AC-1: every template section);
- any `blocking` gap whose question is absent from `## Open Questions` is added
  there as a `- [ ]` item (BR-5, `/spec`'s non-interactive disposition).

### ADR-5: The source goes to the model as segmented, delimited, untrusted data (BR-6)

The source is redacted, then cut into the same 200-line segments `partials/intake.sh`
uses, wrapped in `<source>` / `<segment id="Snn">` tags, and placed in the user
turn. The system prompt states that the source is data and that instructions
inside it are content. The key is never in the prompt. It travels only in the
`x-api-key` header, so the model cannot print it whatever the source says. The
endpoint is a constant in `intake.js`, and the CSP limits `connect-src`. Nothing
in the source can change either.

### ADR-6: Error classes match positively and fall through to `unclassified` (BR-10)

| Class | Positive match |
|---|---|
| `invalid_key` | HTTP 401, or `error.type == "authentication_error"` |
| `rate_limited` | HTTP 429, or `error.type == "rate_limit_error"` |
| `overloaded` | HTTP 529, or `error.type == "overloaded_error"` |
| `budget_refused` | the local BR-4 refusal (with line count and budget), or a provider 400 whose message names the credit balance |
| `unclassified` | everything else: network failure, 5xx, 403, malformed response |

The default branch asserts nothing (LESSON-581). Every displayed message passes
through `scrubSecrets(text, apiKey)`, which removes the exact key and anything the
redaction chain matches, before it reaches the page (BR-1).

### ADR-7: No counters, no storage (BR-8)

A static Space has no server state, and this one adds no analytics script. It keeps
**no** aggregate counter. REQ-672's adoption signals therefore have no Space data to
read beyond what Hugging Face itself shows a Space owner (likes and visits), which
holds no content and no key. BR-8 permits counters and does not require them.

### ADR-8: Default model `claude-sonnet-5-5` (resolves Open Question 4)

Visitors pay, so the default is the strong mid-tier model, not the most expensive.
It lives in `space/config.json` and is shown on the page before any key is entered
(BR-9). Changing it is an edit to that JSON file.

### ADR-9: Anthropic only, no OpenAI-compatible endpoint (Open Question 3)

The first release calls only Anthropic, as the spec assumes. An extra endpoint would
widen the CSP and the key's possible destinations, which is the opposite of ADR-1.
It is left as a follow-up.

### ADR-10: Redaction reuses `/spec`'s chain; no REQ-671 module exists yet

At architecture time (2026-10-29), `main` and the open PRs (#202, #203) carry no
scrub or redaction module from REQ-671, which is still `draft` with no branch. The
Space therefore reuses the 5-pattern chain from `partials/intake.sh`, extracted at
build time (ADR-3), rather than adding a second list. The chain has no `hf_` token
pattern and its env-name arm is uppercase only. Widening it changes every copy
(`/proceed` Phase 5, the delegate pre-pass, telemetry), so that is a follow-up and
not part of this REQ.

### ADR-11: Space ownership and deployment are the maintainer's, outside the pipeline

Open Question 2 (which Hugging Face account owns the Space) is a deploy-time
decision. Nothing in the code depends on it. Creating the Space, pushing to it and
recording its URL in the root README (AC-12, BR-13) happen only with the
maintainer's go-ahead, using the steps `RELEASING.md` gains. Until then the root
README carries no Space link, and the card carries no dataset link (REQ-671 is not
live), per BR-13.

## Plugin and lint surface

`space/` has no `SKILL.md`, so the plugin's `"skills": "./"` scan does not treat it
as a skill. `tools/lint-skills` walks `SKILL.md` files and specific roots. It does
not scan `space/`, and a nested `README.md` with YAML front matter trips no check.
The plugin cache copies `space/` (about 60 KB) with the rest of the tree, which is
harmless.

The Space's tests are JS, so `python3 -m pytest tools` is unaffected.

## Files touched outside `space/`

- `spec/SKILL.md`: two marker comments (ADR-3). Neither REQ-647 nor REQ-654 edits it.
- `RELEASING.md`: a "Hugging Face Space" section (build, check, deploy from a tag).
- `.adlc/context/architecture.md`: a short "Hugging Face Space (REQ-670)" entry.
- `CHANGELOG.md`: an `[Unreleased]` entry.

No file in REQ-647's or REQ-654's footprint is touched.

## Lessons applied

- LESSON-008: model output is untrusted data, rendered as text only.
- LESSON-012 and LESSON-019: the copy is enforced by a build check, not by prose.
- LESSON-581: `unclassified` is the honest default.
- LESSON-606: every input path (paste, `.txt` upload, `.md` upload) normalizes to one source string before the budget check.
